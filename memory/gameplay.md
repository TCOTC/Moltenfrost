# 玩法机制

元素、协同机关与关卡验证场。只记实测或从源码核实过的点。
决策与理由在 `docs/熔霜-游戏设计文档.md`；机制与坑就近写在代码注释里。

## 判定的分工：谁持有事实，谁做判定（2026-09-24 定）

同一个"权威"问题在两类判定上答案不同，依据是**事实在哪一端**：

| 判定 | 判定方 | 复位/生效方 | 依据 |
| --- | --- | --- | --- |
| 异元素地形致命 | 本机 | 本机复位 | 角色位置由它自己那台机器模拟，位置的事实就在本机（见 `player.gd` 文件头） |
| 按钮是否被踩住、门是否开 | 服务端 | 服务端 rpc 广播状态 | "两人是否同时到位"这个事实各端都看不到全局，只有服务端有 |

- 客户端踩按钮到看见按钮反应晚一个 RTT（原型期接受，未实测）。主机自己踩按钮没有这段延迟，
  因此试玩时两边的响应速度会不对称。
- 地形致死各端的 Area3D 都会对**每个**角色触发 `body_entered`（远端角色的位置在本地同样被更新），
  所以处理前必须筛掉非本机角色，否则每一端都会去复位别人。

## 元素分配（2026-09-24）

- 元素按**槽位**奇偶分配：偶数槽（0/2/4）是熔，奇数槽（1/3/5）是霜。两人开局必然一人一种。
- **不能按 peer id 取奇偶**：客户端 peer id 由引擎随机分配（见 `networking.md`），
  两台机器会随机拿到同一个元素。
- 元素随生成包发送（`main.gd` 的 `_spawn_player` → `_instantiate_player`），各端由同一份数据推导。

## 机关门的两种语义（2026-09-24）

- `latched = true`（默认）：每个按钮**曾被踩过**即开启并保持。
  第一关用这个：两个按钮分处被隔墙分开的两条通道，而两人都在按钮上时没有人能去门口；
  门若随松手关闭，这个机关就永远无法通过。
- `latched = false`：只在全部按钮**当前**被踩住时开启，松手即关。
  留给「一人按住、另一人先过」这类结构——那时门必须能关，否则按住的那一方没有存在的意义。
- 历史在 `_physics_process` 里顺手记录，不需要按钮另外发信号：
  检查频率是物理帧，远高于人踩下按钮的时长，不会漏。

## 出口：全部玩家同时在范围内才通关（2026-09-24）

- 判定在服务端（需要「所有人分别在哪」这个全局事实），用可靠传输广播结果。
- 每帧用 `overlaps_body` 逐个核对，而不是自己维护进出名单：
  名单在掉线、复位、瞬移时都要跟着修，而这些恰好是联机里最容易出错的地方。
- **未自动化覆盖**：自动路线无法同时满足「两人各踩自己的按钮」与「两人同时站上出口」两处，
  所以这一条只能人工验证；负例也做不了，因为单人根本走不到出口。

## 复位是一次瞬移，显示端必须识别（2026-09-24）

- 复位把角色从池子直接送回出生点，跨度是米级。接收端若照常按位移插值，
  画面会从池子一路滑回出生点，而途中的位置从未发生过。
- 判据用**收到的原值**（不受显示平滑影响）：相邻两份位置相距超过 `TELEPORT_DISTANCE = 3 m`
  即判为瞬移，清空 `RemoteInterpolator` 的缓冲并按原值显示，随后由后续快照重建时间轴。
- 3 m 的依据：正常同步的相邻两份位置，速度 6 m/s、链路最坏空档按水位上限 350 ms 计也只有 2.1 m。
- 复位必须**同时**重建位移统计基准（`_reset_step_baseline`），否则那一跳会被记进
  `最大单帧位移`——那个数字是"显示是否跳变"的验收指标，混入瞬移就失去意义。
- 清空缓冲之后还要把 `Visual` 子节点的偏移归零。偏移是"插值后的显示位置 − 收到的位置"，
  瞬移后节点位置已经变了而偏移还留在上一段平滑的值上，网格会错开一小段，
  直到下一个快照到达才回正。归零在"无可插值区间"那个分支里做，两种情形（首份快照之前、
  刚被判定为瞬移之后）都需要它。

## 第一关「双通道」的几何（2026-09-24 重做）

第一人称关卡，几何全部由 `scripts/level/level_01.gd` 在运行时生成；尺寸常量集中在那个文件顶部。
`scenes/main.tscn` 只剩入口、`Level`、玩家容器与 HUD。坐标摘要（米，+X 向右、-Z 向前）：

- 房间：x ∈ ±8，z ∈ [-16, 14]，天花板 5.5 米；北墙 z=14，南墙 z=-16。
- 通道中心线 x = ±5，各自宽约 1.8 米。
- 主厅与出口厅以 z = -6 为界。**隔墙在 x ∈ ±0.35、高 3.5 米、从 z=14 一直延伸到 z=-6**，
  所以两人不能串到对方通道——这是「必须两人」的空间依据。
- 出生点 (±5, 1, 13)；同一侧第二个槽位往后每行退 2.5 米（只能调试时多开才会用到）。
- 同元素池（可通行）z = 11，异元素池（致命）z = 2.25，按钮 z = 7.25，均在各自通道内。
- 门：z = -6，宽 5 米（x ∈ ±2.5）、高 3.2 米，开启时下沉 3.6 米并关闭碰撞。
  **门两侧必须封墙**：房间宽 16 米而门只占中间 5 米，不封就能绕过门直达出口（已补 `GateSide*`）。
- 出口：(0, 0.6, -12)，判定体 3.2×2.4×3.2。

摆位为什么贴着车道：`--autopilot` 从出生点沿 -Z 走 `AUTOPILOT_RUN = 16` 米再返回，
因此「同元素池 → 按钮 → 异元素池」自动落在同一条路线上，冒烟测试一次就能验证三种判定。
自动驾驶会同时把朝向转到行进方向——第一人称下必须转身，否则画面表现为横着平移。
改动这些坐标前先看 `tools/net-smoke.mjs` 的断言，它依赖这套几何。

## 冒烟测试的覆盖（2026-09-24）

`tools/net-smoke.mjs` 起三个实例：无头专用服务端 + 两个客户端（都带 `--autopilot`）。
除原有的连接、生成、平滑之外，新增：

- 客户端（槽位 0，熔）走进霜池后被复位——覆盖元素分配、地形判定、复位同步。
- 服务端判定客户端踩下熔按钮——覆盖按钮的检测范围。
- 只有一个按钮被踩住时门不开——覆盖门的判据是"全部按钮"。
- 第二个客户端（槽位 1，霜）加入后，两个按钮同时被踩住的那一刻门在服务端打开，并广播到客户端
  ——协同机关唯一的正向验证，也是目前唯一需要**两个玩家**才成立的断言。

未覆盖、只能由人试玩判断：门从踩下到画面反馈的时延、异元素池子复位的突兀感、
两人同时到达出口、双人配合的节奏。
