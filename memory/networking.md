# 联机

机制与坑。只记实测或从源码核实过的点；决策与理由在 `docs/熔霜-游戏设计文档.md` 4.5。

## 结论：权威节点自建，不用 Steam 中继或 EOS

- 2026-09-24 定。分歧点只有一个：由谁解决可达性。本项目面向的玩家与两台开发机都没有公网入口，
  因此只有"权威节点自带公网地址"这一条能从根上移除这个问题。
- Steam 数据报中继（SDR）：免费、零服务器，但官方文档明确非 Steam 渠道不保证服务，且需要 AppID。
- EOS P2P：免费且不要求上架 Epic，但 Godot 侧绑定由社区维护，与 4.7.2 的匹配情况未核实。
- 自建：一台最便宜的 VPS。代价是月度费用，并发上限等于进程数（一个无头进程服务一场对局）。
- **服务端必须是同一份 Godot 工程**，理由不是省事：服务端要执行物理与机关判定，
  另用一套实现就要重写 Jolt 的刚体动力学与碰撞求解，而两套实现必然分叉。

## 无头服务端

- `--headless` 等价于 `--display-driver headless --audio-driver Dummy`，Godot 4 起不需要单独的 server 版二进制。
- 判定方式：`DisplayServer.get_name() == "headless"`，或用导出预设的 `dedicated_server` 特性标签
  （Resources 页选 Export as dedicated server，可对贴图/材质选 Strip Visuals 显著缩小 PCK）。
- **服务端不能依赖渲染**：Strip Visuals 之后贴图被占位替代，任何读取图像像素的判定都会失效。
- **服务端不是玩家**：官方文档明确提醒示例代码默认把服务端当成一个玩家。本工程的规则是
  "本机是否为玩家只取决于运行模式，与它是权威节点这一点无关"。

## 实测：2026-09-24

### 客户端 peer id 是随机的，不是 2

服务端日志实测：`peer 1480001058 已连接`、`peer 799416377 已连接`，两次都不同。
`High-level multiplayer` 文档也写了"客户端被分配一个随机的正整数"。
**任何按顺序假设 id（第一个人是 2）的代码都会错。** 冒烟脚本因此从日志里正则取出 id 再用。

### 权限必须设在 `_enter_tree`，不能等 `_ready`

- 接收方在远端生成包到达的同一帧就应用初始同步状态，而那一刻它要求节点的多人权限
  已经等于发起方——`SceneReplicationInterface::on_replication_start` 里有
  `pending_spawn == obj_id && sync->get_multiplayer_authority() == pending_spawn_remote` 这个判断。
- **权限不随生成包传输**（`_make_spawn_packet` 里没有权限字段），所以各端必须各自推导出同一个值。
  本工程的做法是在生成函数里传入 peer id，`_enter_tree` 里 `set_multiplayer_authority(peer_id)`。
- 源码核实：`Node::_propagate_enter_tree()` **不**处理 `multiplayer_authority`，
  只设置 tree/depth/viewport 与分组，然后发 `NOTIFICATION_ENTER_TREE`。所以在 `add_child` 之前
  设置权限不会被父节点覆盖；反过来，权限也不会自动从父节点继承。
- `MultiplayerSynchronizer::set_multiplayer_authority` 是重写版本，会先 `_stop()` 再 `_start()`，
  因此改权限等于重新注册同步，不要频繁调用。

### `MultiplayerSpawner.spawn_function` 不会被序列化

`ADD_PROPERTY(..., PROPERTY_USAGE_NONE)`，所以它写不进 `.tscn`，**必须在每个 peer 上于运行时赋值**。
用自定义生成（`spawn(data)`）而不是 `add_spawnable_scene` 的好处是生成参数随包发送，
不需要再从节点名反推 peer id。

### 迟到的 peer 能收到已有的生成（源码核实）

`SceneReplicationInterface::on_peer_change(id, true)` 会遍历 `spawned_nodes` 并逐个
`_update_spawn_visibility(p_id, oid)`，因此"主机先开局、客户端后加入"这个常见顺序是被支持的，
不需要自己重发生成。

### 生成节点名的限制

- 必须通过 `Node::validate_node_name()`：不能以 `@` 开头（引擎的自动名），不能含 `. : / " %`。
  所以添加生成节点时要 `add_child(node, true)`（第二个参数让引擎生成可读名），或自己起合法名。
- 同一父节点下必须唯一（`on_spawn_receive` 里 `ERR_FAIL_COND_V(parent->has_node(name))`）。

### `SceneReplicationConfig` 的三种模式与 `.tres` 写法

- 枚举：`NEVER = 0`、`ALWAYS = 1`（每个网络帧以不可靠方式发送）、`ON_CHANGE = 2`（变化时以可靠方式发送）。
- 序列化键：`properties/N/path`、`properties/N/spawn`、`properties/N/replication_mode`。
  注意 `_get_property_list` 把 `path` 声明为 STRING 但 `_set` 要求 `Variant::NODE_PATH`，
  且子名数必须大于 0，所以文件里要写 `NodePath(".:position")` 而不是裸字符串。
- `spawn = true` 的属性在生成包里随初始状态一起送达；`ALWAYS` 的属性按网络帧持续发送。

### 主机的本机玩家要显式生成

`multiplayer.peer_connected` 只在**别的** peer 连接时触发，主机自己不会收到针对自己的信号。
所以 listen server 模式必须在 `Net.host()` 成功之后立刻为 `Net.local_id()` 生成一次角色。
（2026-09-24 就是漏了这一条，无头测试看不出来，因为专用服务端本来就不该有本机角色。）

### 没有 peer 时 `multiplayer.is_server()` 返回 true

离线状态也被当作服务端，所以无法用它区分"未开始会话"与"正在监听"。
本工程用 `Net.role`，并把"本机是否权威"定义为 `role != CLIENT`。

### 生成位置要按 peer id 错开

否则所有玩家重叠在原点。本工程按 peer id 分布在一个半径为 4 的圆上。

### macOS 客户端连 Windows 主机（2026-09-24 实测，两台真机）

- 同一 Wi-Fi 网段（Mac `192.168.5.190`，主机 `192.168.5.210`），客户端 `--join 192.168.5.210 --port 27015`
  一次连上，没有额外开防火墙规则。客户端日志顺序：
  `已连接到主机` → `peer 1 已连接` → `远端角色 peer=1 已就位` → `本机角色 peer=787917097 已就位`。
- 客户端视角里主机 peer id 是 1，与服务端的约定一致。
- **`ping` 不通不能当成不可达**：Windows Defender 防火墙默认丢弃 ICMP，而 UDP 27015 是通的。
  判断可达性只能看客户端日志里的连接结果。
- macOS 命令行的 Godot 在 `/Applications/Godot.app/Contents/MacOS/Godot`，直接带 `-- --join …` 跑工程即可，
  `window/size/mode.editor=0` 覆盖生效所以是窗口模式（日志里的 `[display]` 行会打出「生效模式=窗口」）。
- 这次仍**没**验证位置同步是否真的在流动（要人按键）、延迟与丢包。

### 两台开发机的链路实测（2026-09-24）

Windows 机器（主机侧）：MediaTek Wi-Fi 6 MT7921，802.11ax，5 GHz 信道 44（SSID `507-5G`），
协商速率 1201 Mbps，RSSI -55 dBm。**没有有线网卡在用**（另一张是 VMware 虚拟网卡）。

```text
到网关 192.168.5.1：丢包 0/40，min 2 / avg 2 / max 3 ms
到 223.5.5.5：丢包 0/20，min 43 / avg 43.5 / max 44 ms，抖动 0.5
到 119.29.29.29：丢包 0/20，min 37 / avg 38.6 / max 69 ms，抖动 7
到 8.8.8.8 / 1.1.1.1：181 / 173 ms（国际路由，不反映国内服务端时延）
```

结论：**这一段链路本身是健康的**（局域网 2 ms、无丢包、抖动近于零）。
远端角色的显示滞后不来自链路时延，而来自两处：平滑水位（自适应，链路差时才抬高）
与发送方物理帧率。唯一的无线残余风险是省电投递的成簇空档（见上），
`--net-stats` 的 `最大连续间隔` 是否出现 100 ms 左右的离群值即可判断。

自建公网服务端的时延预算：国内目标 37～44 ms 的 RTT 对应单程约 19～22 ms，
与平滑水位（50～150 ms）相加仍在双人解谜可接受的区间内。

## 命令行与日志

## 冒烟测试（`tools/net-smoke.mjs`）

- 无头起一个专用服务端与一个客户端（`127.0.0.1`），按日志断言：
  服务端开始监听 → 客户端连接成功 → 服务端收到连接并生成角色 → 客户端收到自己的角色
  → 专用服务端未生成本机角色 → 两个实例均在运行且无脚本错误。
- 它顺带验证了输入映射：客户端会执行本地玩家的 `_physics_process`，

- **它不覆盖的事**：位置同步是否真的在流动（玩家不动就看不出）、手感、延迟、丢包、

  局域网的 1 ms RTT 与真实公网差距太大，不能让局域网测试的结论代替。

## 远端角色卡顿（2026-09-24，查了三轮）

### 现象

长按直走时，别人看到远端角色不连续。实测出现过两种形态，**根因同一个，但表现相反**：

| 形态 | 做法 | 看到的现象 |
| --- | --- | --- |
| A | 不做任何处理（最早） | 走一下、停一下，节奏固定 |
| B | 只加固定延迟插值 | 看起来毫无变化（形态 A 的延迟平移） |
| C | 加插值 + 开外推 | 快速往回一点再继续（橡皮筋） |
| D | 加插值 + 关外推 | 停一下再瞬移 |

根因有两条，各自独立，必须都修（三条里第一条是前提）：

1. **快照里夹着重复位置**（形态 A 的直接成因）：发送方位置只在物理帧变化（60 Hz），
   快照却按网络帧发送（120 次/秒），因此约一半快照携带与上一份相同的位置。见下一节。
2. **延迟小于最坏空档**（形态 C 与 D 的共同成因）：见"最终根因"一节。
   注意它不是我第一轮以为的"间隔普遍很大"，而是"多数间隔很小、偶尔很大"。

引擎不做插值这一层从来不是根因，但它是前提：接收方直接把每个快照赋给节点
（`on_sync_receive` → `MultiplayerSynchronizer::set_state`，源码核实），
所以任何不连续都会直接表现在画面上。

### 实测数据（同机环回）

用 `--net-stats` 量到的同步包到达节奏：

| 场景 | 每秒更新 | 到达间隔 |
| --- | --- | --- |
| 两个无头实例 | 137～145 次 | 7～8 ms |
| 两个带窗口实例（同一张显卡） | 111～120 次 | 16～18 ms（最大 91） |

**这一页数据一度把我带偏**：到达节奏确实均匀且无丢包，因此我当时排除了传输层，
把方向定在插值参数上。但真正的第二个根因（间隔大于 delay）在环回链路上永远不出现，
所以本机复现不了、只能靠用户的实测数据。教训：环回只能验证“逻辑对不对”，
不能验证“参数够不够”。

`--quit-after` 用小数帧数测不到这些数：无头模式不限帧，几百帧不到两秒就跑完了，
而统计间隔是两秒，所以要按墙钟时间跑（或把 `--quit-after` 放大到几千）。

### 最终根因：延迟必须覆盖**最坏空档**，而不是多数间隔

前两轮的结论都不完整，第四轮拿到两台真机的日志后才定下来。
用户那条链路的实测（Windows 主机观察 Mac，60 次/秒的流）：

```text
实时间隔=17 ms（最大 100）   重复=2%~37%   保持=11%~42%   停格=18~94/241 帧
```

- **绝大多数间隔是 17 ms，但偶尔出现 100 ms 的空档**（笔记本无线链路的省电与调度抖动很典型）。
- 按“多数间隔”定的延迟（60 ms，即我当时的下限）会被这种空档击穿：目标时刻越过最新快照，
  没有可插值的区间，只能保持，到货后再跳过去——就是“卡一下再瞬移”。
- 正确做法是**按实测的最坏空档定**，而不是按分位数或平均值。
  注意“按最坏空档定”并不等于“写死一个常量”：常量在好链路上会白白多等。
  最终实现是按实测的**最大连续间隔**动态定（第七轮），常量只当上限与默认值兜底。
- 我第三轮的自适应取的是 90 分位（17 ms）×2 = 34 ms→被下限抬到 60 ms，
  **分位数把造成停顿的那几次整个漏掉了**。这是第三次修改也无效的原因。
- 另一个反例证明不能拿“保持比例”做反馈：对端静止时快照全被丢弃，
  显示必然一直保持（实测 Mac 侧 `保持=100%`），按它调参会把延迟推到上限。

### 做法：时钟调速 + 自适应水位

共七轮才收敛，各轮的贡献分开看：

- **时钟调速（第四轮）**：显示时刻按可变钟速前进，缓冲偏少则减速、偏多则加速。
  关键在于**调整只改钟速、显示时刻永远单调前进**，因此任何调整都不会造成位置跳变；
  固定延迟做不到这一点（改 delay 等于把显示时刻往回挪，就会看到倒退）。
- **水位按实测自适应（第四轮试、第七轮做成）**：水位 = 实测最大连续间隔 × 1.3，夹在 50～350 ms。
  第四轮失败的原因是**把静止时长也当成空档计入**：静止时长可达几秒，
  会把水位推向上限（实测 2 秒静止即到 400 ms），于是对端每停一次、永久滞后就增加一次。
  第七轮加了速度估计之后，只有**连续运动**的间隔参与估算，因此静止不再污染它。
  实测收益：同机环回上空档 17 ms → 水位自动降到下限 50 ms，比固定 150 ms 省 100 ms。
- **静止后重新移动必须重新锚定显示时刻，且只能向前**。对端不动则位置不变、快照全被丢弃，
  最新快照的时刻不再前移；显示时钟追到前沿停下（此时“停顿”是正常的）。
  等对端重新移动，最新快照时刻一次性前移整段静止时长；
  若把它当成落后量，显示要用很久去“追”那段从未发生的运动——**实测滞后曾达 1421 ms**。
  修法是把显示时刻设回“新数据之前一个水位”处；
  用 `maxf` 而不是直接赋值，因为静止短于水位时直接赋值会把显示时刻往回移（第六轮）。
- **“停顿”只在数据仍在流动时才计入统计**（距上次有新位置 250 ms 内）。
  否则对端静止时它恒为 100%，完全掩盖真正的停顿（实测就出现过这种误读）。
- 单帧时长要夹上限（100 ms）：系统卡顿会让某一帧长达上百毫秒，
  全额推给显示时钟会一次跳很远而直接撞上前沿。

### 最终根因（第五轮）：时间戳必须来自发送方，不能用接收时刻

上面第 3 点（缓冲）修好了巨大的滞后，但"每隔一段时间卡一下"仍然存在。
真机日志里的一条数字给出了答案：

```text
每秒到达=60.5 次   最大到达间隔=100 ms   重复=8%   显示移动=10.22 m
```

**`重复=8%` 是决定性的**：60 次/秒的到达里只有 8% 是重复的，意味着近 92% 携带不同的位置，
而物理帧率是 60 Hz——不可能产生 55 个不同的位置/秒。唯一解释是：
**多份位置被一次性投递进来**（无线链路省电缓冲，约每 100 ms 成簇）。

而问题出在打时间戳的方式：**用了"接收时刻"**。于是

- 一簇里 5～6 份不同位置全被标成几乎同一时刻；
- 插值在这条时间轴上会：平稳走到簇内第一份，然后**一帧内跳到簇内最后一份**
  （因为中间样本的时刻几乎相同），之后等下一簇；
- 表现就是**平稳→跳一下→停一下**。
- **这个跳与水位大小无关**，因为它是数据在时间轴上的摆放方式造成的，不是缓冲不足。
  所以第四轮调水位、第三轮改延迟都不可能修好它。

修法：发送方随每次同步发出自己的时刻（`Player.sync_time`，在 `_physics_process` 里更新，
与位置变化同帧，因此两者描述同一个时刻），接收方用它给快照排序。
这样一簇里 100 ms 的运动量会被摊到 100 ms 的显示时间里。
因为只用到"最新快照时刻减去显示时刻"这类差值、且两端时间同一速率，不需要估计时钟偏移。

验收指标：`最大单帧位移`。角色 6 m/s、120 帧显示时，平滑运动每帧只应前进 0.05 m；
修好后实测 0.05～0.06 m，修好前是 0.5 m 量级。

### 时间戳的坑：初始值 0 会污染时间轴

`sync_time` 必须**不随生成包发送**（`spawn = false`）。因为生成发生在第一物理帧之前，
那时 `sync_time` 还是 0，而后续同步包带的是"引擎启动以来的毫秒数"（几千），
两者相差几秒，会把时间轴一次性推远：实测表现为 `缓冲=990/150 ms`、
钟速长时间卡在上限 1.10 一直追不上。
同理，`_ready` 里也不能用**本机时刻**先推一份初始快照，否则两个时间轴被混在一起。
另外 `RemoteInterpolator` 里有一道安全网：快照间隔超过 2 秒即当作时间轴重启。

### 100 ms 空档来自哪里（无线链路的省电投递）

  而同一日志里发送方的 `位置更新` 间隔是 17 ms。
  **这种精确程度不像随机抖动，而是无线网络的 beacon/DTIM 周期**：
  终端处于省电模式时，接入点缓存下行数据、按该周期成簇投递。
- 隔离方法：在主机上再开一个客户端连 `127.0.0.1`，与另一台机器同时连上。
  主机日志会出现两个远端行，本机客户端（不经无线）应报十几毫秒，
  另一台报 100 ms 左右。两者一旦相差明显，空档来源就确定了。
- 缓解手段在链路层而不在代码：有线网、5 GHz、关闭网卡省电、缩短与接入点距离。
- 诊断输出里本机行是“发送方基准”（`位置更新` 与 `最大间隔`），
  与远端行的 `最大到达间隔` 对照即可判断空档在链路还是在本机的帧/物理。


本机实测（双窗口、120 fps、60 Hz 物理）：`停顿=0%  缓冲=45~55/50 ms  钟速=0.98~1.02×  停格=0/241 帧  回拉=0`。

### 两台真机的日志还说明了什么

- Mac 侧渲染 60 fps（帧时稳定 16.7 ms），Windows 侧 120 fps；
  因此 Mac 发 60 次/秒、Windows 发 120 次/秒。**两台的发送频率不一样，平滑参数不能按“帧率”假设。**
- 断开时客户端会正常输出 `peer 1 已断开` 与 `与主机断开`，且无报错（前一个提交修好的那个问题已验证）。
- **本机 role=1 那一行永远是 `实时间隔=0 / 延迟=0`**：本机角色不创建插值器，这些字段对它是空的。
  看远端角色那一行才有意义。

### 静止→移动这个转换上有两个坑（第六轮）

`最大单帧位移` 这个读数直接指出来了：真机上曾出现 `最大单帧位移=0.75 m`
而与 `显示移动=0.75 m` 相等，即一帧之内走完全部位移。它总在"对端开始移动"时出现。

- **坑一：插值把整段静止时长当成匀速位移。** 对端静止时位置一直不变、快照全被丢掉，
  所以时间轴上最后两个快照之间隔着整段静止时长。插值在这段上按直线推进，
  于是目标时刻取在"新数据之前一个水位"时已经跳过了大部分距离。
  修法：用位移量与速度估计比较，判断这段间隔里对象是否真的在动：
  **|ΔP|/间隔 接近速度估计 → 连续移动中的发送停顿**（发送方自己卡帧，Windows 侧实测帧时到过 83 ms），
  直接插值；**远小于速度估计 → 静止后重新移动**，补一个保持点
  （在 `sender_time - 步长` 处仍写原位置），把位移摊在正常的一步之内。
  两种成因需要完全不同的处理，只看间隔大小区分不了——这一点是我第一次改时踩的。
- **坑二：重新锚定只能向前。** 静止时长小于一个水位时，
  "新数据之前一个水位"落在旧显示时刻之前，直接赋值会让显示时刻倒流、画面倒退，
  再由钟速慢慢补回来（同一次 0.75 m 的反向跳）。改用 `maxf`。
- 验收：`--autopilot-stop`（交替运动与静止各一秒）下实测 `最大单帧位移=0.05 m`，
  与连续运动时一致；修复前是 0.75 m。
- 步长估计取自最近间隔的**最小值**（对应发送方连续两个物理帧各发一份），
  而不是平均值：平均值会被静止时的长间隔拉大。
  它现在只作为"这段位移该占多长"的下限，不再直接决定保持点的位置（见下一节）。

### 三台机器一起跑时暴露的两个新根因（2026-09-24 晚）

场景：Windows 主机 + Windows 本机客户端（`127.0.0.1`）+ Mac 客户端，一共三个角色。
用户反馈"间隔卡顿又出现了，不过没有最开始那样明显"。日志给出的读数是：

```text
Mac 侧观察一个正在移动的角色：
  每秒到达=60.5 次  最大到达间隔=100 ms  重复=0~7%  停顿=5%~20%
  缓冲=44~99/108 ms  最大连续间隔=83 ms  钟速=1.10×
  最大单帧位移=0.17 m（正常应 0.05 m）当时：滞后 67/50 ms

Windows 侧本机（发送方）：
  位置更新=57.0 次/秒  最大间隔=650 ms（另有 483 ms、117 ms）
  帧时=0.2～83.3 ms
```

两个根因彼此独立，而且**都不是网络时延问题**（RTT 只有 8～16 ms，且回环链路测不出它们）。

#### 根因六：发送方掉步会让时间轴被拉长，而补保持点只退一个物理步

发送方的位置只在物理帧变化，帧时尖峰到 83 ms 时引擎会在一个渲染帧里补跑 5 个物理步
（补满，没问题）；但尖峰到 **483 ms / 650 ms 时超过了 `max_physics_steps_per_frame`
（默认 8 步 = 133 ms）**，物理补不满，于是：

- **墙钟（也就是随包发出的时间戳）前进了 650 ms**
- **位置只前进了 8 步的量（约 0.8 m）**

接收方看到的是"间隔 650 ms、位移 0.8 m"，`moved/gap` 只有 1.2 m/s 而不是 6 m/s，
于是被判为"非连续"，走补保持点那条路。而保持点原来固定在 `sender_time - _step_estimate()`
（一个物理步 ≈ 16.7 ms），结果 **0.8 m 被压进一帧**：单帧位移 0.36～0.75 m。
把 0.8 m 用 133 ms 摊开才是对的。

修法：保持点的位置改为 `sender_time - expected`，其中
`expected = |ΔP| / 速度估计`（这段位移按速度估计该占的时长，下限取物理步长）。
同时**重新锚定也要退到保持点之前**（`maxf(buffer, expected)`）：
只退一个水位会让显示从保持段末尾起步，照样一帧走完整段位移。

判据也一并改成与 `expected` 比较（`gap <= expected × 1.5` 视为连续），
而不再与"半个速度估计"比较。两者在匀速空档下等价，但前者能同时表达
"位移大、间隔也大"（掉步，仍是连续）与"位移小、间隔大"（静止后重新移动）。
实测把 `expected` 换回固定物理步长，连**既有**的两条用例都会失败
（停顿 14.8%、单帧位移 0.29 m），所以这不是可选的美化。

#### 根因七：水位只按发送方时间戳估，看不出链路的到达空档

水位要盖住的是"接收方多久没有新数据"。而发送方的时间戳间隔**看不出**链路把若干份
攒到一次投递——那种情况下时间戳仍然是连续的 1/60 秒，只有本地到达间隔能反映它。
实测 Mac 侧水位 108 ms、而 `最大到达间隔` 是 100～120 ms，恰好差一点点，
于是每个簇之间停顿一次（5%～20%）。

修法：间隔样本取"发送方时间戳间隔"与"本地到达间隔"的**较大者**，
其中到达间隔只在连续运动时取样（否则静止时长会混进来，那是第四轮踩过的坑）。
`push()` 因此多收一个本地墙钟参数（默认省略时退化为时间戳，便于离线测试）。

#### 读数本身的缺陷：总览行的水位被静止角色抬高

`估计显示滞后` 取所有远端角色水位的**最大值**。一个从头就静止的角色
（主机侧那个角色全程没动）不会产生水位样本，水位一直停在初始值 150 ms，
于是总览行报 175 ms、而远端行里那个正在动的角色只有 108 ms，看起来自相矛盾。
修法：总览行只统计**正在接收位置更新**的角色（`is_receiving_motion()`），
都对端静止时报"无可测对象"。

#### 顺带确认的性能事实

Windows 上同时跑两个 Godot 实例（主机 + 本机客户端）时，帧时尖峰到 83 ms、
物理帧间隔尖峰到 650 ms。这不是代码问题，而是同机争抢 CPU/GPU：
**调试联机时不要在同一台机器上开两个带渲染的实例**，那是取不到干净数据的。

### 延迟的构成（2026-09-24 实测）

平滑稳定之后，`--net-stats` 的总览行给出四项构成。这是回答"延迟由哪些部分组成"的地方：

```text
RTT=14 ms  估计显示滞后≈69 ms（水位 50 + 单程 7 + 发送 8 + 本机一帧 4）
```

### 帧率对照（2026-09-25 实测，同机环回，显示帧率 120 fps）

`--physics-hz` 是为此加的临时覆盖开关（默认沿用工程里的 60）。

| 发送方物理帧率 | 重复快照 | 最大连续间隔 | 估计显示滞后 |
| --- | --- | --- | --- |
| 60 Hz（默认） | 50% | 17 ms | 66 ms（水位 50 + 单程 4 + 发送 8 + 本机一帧 4） |
| 120 Hz | 0% | 9 ms | 62 ms（水位 50 + 单程 4 + 发送 4 + 本机一帧 4） |

- 重复率约等于 `1 - 物理帧率 / 显示帧率`：显示 120 fps 而物理 60 Hz 时正好一半。
- **提高物理帧率只省 4 ms**（发送项 8 → 4），代价是物理开销与快照量翻倍 → 暂不采用。
- 显示帧率高于物理帧率时，多余的帧只用于插值取样（运动更平滑），不带来新信息。
- 注意 `--max-fps` 会被 vsync 压到显示器刷新率：本机显示器 120 Hz，
  所以写 `--max-fps 240` 实际仍只有 120 fps（对照实验里要留意这一点）。

| 项 | 来源 | 实测（同机环回） |
| --- | --- | --- |
| 水位 | 平滑缓冲，代码可控 | 50 ms（按实测最大连续间隔 17 ms ×1.3 再夹到下限） |
| 单程时延 | RTT/2，由每秒一次的 ping/pong 实测 | 7 ms |
| 发送方物理步长（半个） | 位置只在物理帧变化 | 8 ms @ 60 Hz |
| 本机一帧（半个） | 自己渲染一帧 | 4 ms @ 120 fps |

**水位曾经是固定 150 ms**，那是按用户链路的 100 ms 空档定的。改回自适应后，
同机环回上它自动降到下限 50 ms——**省下 100 ms**。这给出优化顺序：
先把链路改好（有线 / 5 GHz / 关省电），水位会自动跟着降；否则它会一直吊在链路的空档上。

### 水位自适应与静止时长的坑（第七轮）

自适应本身在第四轮试过，当时失败的原因是：**静止时长本身是一次极大的"空档"**，
它会把水位推向上限（实测 2 秒静止即到 400 ms），于是对端每停一次、永久滞后就增加一次。

第六轮加入的速度估计把这个问题解掉了：现在只有**连续运动**的间隔才计入水位估算，
静止时长既不参与估水位、也不参与估步长。测试里有两条用例分别守住这两件事：
`_case_buffer_adapts_to_link`（水位随链路变而变）与
`_case_stationary_does_not_inflate_buffer`（静止不得抬高水位）。

`--interp-buffer <秒>` 现在会把 `adaptive` 置为 false，也就是固定水位，仅用于对照。

### 水位的第二层：按实测卡顿时长补偿（第九轮）

水位 = **链路基准** + **卡顿补偿**，相加后夹在 50～350 ms：

- **链路基准** = 最近 GAP_WINDOW 个连续运动间隔的最大值 × 1.3，夹在 50～350 ms。
- **卡顿补偿** = 实测的卡顿时长（夹在 0～STALL_PENALTY_MAX = 60 ms），按半衰期 8 秒衰减。

为什么需要第二层：基准取的是"**已经见过**的最坏间隔"，而最坏值总是事后才知道，
所以下一次更长的空档仍会击穿它。真机日志正好演示了这一点——
水位 108～141 ms 一直在跟着 83～108 ms 的间隔走，却仍有 3%～7% 的停顿，
说明造成停顿的那几次比窗口里的最大值更长（30 秒里每约 2 秒一次）。

三个约束与实现对应关系：

| 要求 | 实现 |
| --- | --- |
| 以延迟最小为先 | 没有卡顿时补偿为 0，水位就等于基准；环回实测水位恒为 50 ms |
| 反复卡顿才调大 | 只在卡顿**发生的那一刻**抬高，且只有 30～200 ms 的卡顿计入 |
| 不能太大 | 单次最多 60 ms；总和仍受 MAX_BUFFER = 350 ms 限制 |

实现要点：

- 卡顿的起止由显示时钟是否追到前沿（`_holding`）直接判定，**用的是真实的冻住时长**，
  而不是"保持帧数比例"：比例对短卡顿与长卡顿一样大，区分不出严重程度。
- 时长范围是必需的，不是保险。**上界挡住的是对端静止**：静止时显示必然一直保持，
  而它结束的时刻正是对端重新移动的时刻，于是量到的时长是整段静止（秒级）。
  第四轮就是因为把这种保持计入，水位才被推到上限。
- 下界挡住的是抖动噪声（一次 40 ms 的保持可能只是显示帧错位）。
- 起点的资格还要额外判断"数据仍在流动"（距上次有新位置不超过 FLOWING_WINDOW），
  以及开局预热（`STALL_WARMUP` 份快照）——开局水位还在学，那时的卡顿不代表链路特征。
- 衰减放在 `advance()` 里按显示帧推进，因此不依赖 `push()`（对端静止时就收不到新数据）。

实测响应（同机、好链路起步，插入到达延迟）：

| 插入的到达延迟 | 补偿 | 水位 |
| --- | --- | --- |
| 80 ms | 32 ms | 82 ms |
| 150 ms | 58 ms | 108 ms |
| 250 ms | 58 ms（受上限） | 108 ms |

衰减：4 秒后 41 ms、12 秒后 20 ms（半衰期 8 秒）。测试里两条用例分别守住
`_case_stall_raises_buffer_then_decays`（抬高、封顶、衰减回基准）与
`_case_stationary_does_not_raise_stall_penalty`（静止不得抬高补偿）。

### 几个曾经误导过我的诊断口径

- **`最大单帧位移` 与 `显示移动` 变大，先看角色是不是在自由落体。**
  地面只有 20×0.5×20（±10 m），出生点在半径 4，**没有任何死亡平面或重生**，
  所以走出边界就一直往下掉。实测（三机测试时）：Windows 侧本机报
  `显示移动=60.32 m`，Mac 侧对同一个角色报 `显示移动=63.28 m`、`最大单帧位移=0.91 m`。
  算术即可判定：6 m/s 的走路速度在 2 秒里最多 12 m，而单帧 0.91 m（60 fps）等于 55 m/s。
  关键在于那些跳跃的 `当时` 上下文一切正常（保持=否、滞后在水位内、钟速≈1.0），
  说明插值器只是在如实跟随一个真实很快的位置——**不是平滑缺陷**。
  判据：`最大单帧位移` 异常时先除以帧长算速度，与 `MOVE_SPEED` 比较。
- **到达间隔 ≠ 快照间隔**。`最大到达间隔` 把"位置不变"的重复快照也算进去，
  因此看起来很大（实测 40～100 ms）而与显示无关；定水位用的是**丢弃重复快照之后**的空档。
  两者不是一个东西，混用会得出矛盾结论。
- **判“回拉”不能简单数倒退：掉头也是倒退。** `StepAnalyzer` 只计"退一步后立刻恢复原方向"。
  这一点靠数据发现：本机角色（完全无同步）当时也报出回拉，数值恰好等于一个物理步长——
  那就是我自己的自动驾驶在折返。
- **不能用“保持比例”做反馈**：对端静止时必然持续保持（见上）。
- **速度估计必须有一条回落路径，单边判据会永久锁死**。
  连续运动的条件是 `|ΔP|/间隔 ≥ 速度估计 × 0.5`，而速度估计只在连续时才更新——
  于是它一旦被高估就再也降不回来，此后所有正常间隔都被判成“不连续”，
  `_gaps` 与水位永远不再更新。
  触发方式是发送方**开局切换物理帧率**：头两个间隔实测只有 3～4 ms（稳定后 8～9 ms），
  这两个错位样本把速度估计抬到 12～16 m/s，而角色实际只有 6 m/s，
  于是 `6.0 ≥ 12.6 × 0.5` 恰为假，判据从此失灵。
  症状：`最大连续间隔` 固定在远小于物理步长的值上（实测 1～9 ms，应为 17 ms），
  水位恒为下限 50 ms，**链路变差时水位不再抬高**（会重新出现卡顿），
  而 `停顿=0%` 完全正常。
  修法：三分支——连续运动（收入样本）、大间隔（补保持点）、
  **小间隔且速率明显偏低（让速度估计跟上来）**。
  验收：修复后 60 Hz 下报 17 ms、120 Hz 下报 9 ms（均等于发送方物理步长），
  且链路出现一次 46 ms 抖动时水位从 50 抬到 53 ms。
- **环回验不了参数**：本机空档 8～18 ms，用户链路最大 100 ms。
  环回只能验证“逻辑对不对”，不能验证“参数够不够”。

### 早期做法（仍然必要，但不足以解决问题）

- `scripts/net/remote_interpolator.gd`：存 (时刻, 位置) 快照，用一个可变钟速的显示时刻在快照之间取样并线性插值。
  早期写的是 `now - delay`（固定延迟），第七轮改为“显示时刻按钟速前进”，因为只有后者能保证显示时刻单调、调整不产生跳变。
  已移除的做法：把延迟写在 `position` 上（会让判定跟着延后）、无上限外推（会在对端停下时多走一段）、
  固定默认延迟常量（在好链路上是白等）。
- **丢弃位置未变的重复快照**：见下一节，这是真实的缺陷修正。
- **延迟只作用于显示**：取样结果写到子节点 `Visual` 的局部偏移，
  节点的 `position` 始终是收到的原值。这一条不能省：listen server 既是权威节点、又有画面，
  若把延迟位置写回 `position`，机关同时触发这类判定就会跟着延后。
- 无头时不创建插值器（没有画面，且判定要用原值）。

### 根因一：快照里夹着重复位置

这一点最不显眼，也最贵：

- 发送方的位置只在**物理帧**变化（默认 60 Hz），而快照按**网络帧**发送（显示 120 fps 时 120 次/秒）。
  于是流里大约**每两份就有一份携带与上一份相同的位置**——实测 `重复=50%`，与这个比率吻合。
- 若把重复快照也当作时间轴上的一个点，插值会认为"这 8 ms 内位置没变"，
  然后在下一份快照处用双倍速度补上。显示效果与"每个物理帧跳一步、其余帧不动"完全一致，
  也就是**固定节律的走一下停一下**（与用户描述的"固定间隔"吻合）。
- **这种情况下调大延迟毫无作用**，因为失真已经在收到的数据里，延迟只能把它平移到更晚。
  这正是"按建议调了参数但完全没变化"的原因。
- 修法是**在接收端丢弃位置与上一份相同的快照**，让时间轴只保留真实变化。
  丢弃后快照间隔就等于发送方的物理帧间隔，插值得到的运动是匀速的。
  不必担心"角色停下了却不更新"：位置不变时保持上一个值本来就是正确行为。
- 实测：修复前远端显示在运动中约 **50% 的帧位不变**；修复后为 **0/241 帧**。


### 另一件事：本机自己的位置变量也在"停"

`--net-stats` 里本机角色恒为约 `停格=50%`（实测 110～121 / 241 帧）。
这**不是缺陷**：本机位置由物理帧更新（60 Hz），而显示帧是 120 fps，
用 `global_position` 在 `_process` 里取样必然有一半的帧取到同一个值。
它只说明取样口径与物理帧率的关系，不代表渲染层在抖。
若将来要消除 60 Hz 台阶，正规做法是启用 `physics/common/physics_interpolation`；
但那会与"手动写 `Visual.position`"冲突（父节点被插值、偏移却按物理值算，会相互抵消出抖动），
所以要连同远端平滑的做法一起改，不能单独打开。

### 权衡

- 水位就是“保证不保持”的代价：水位越大越不容易停顿，但显示的滞后也越大。
  自适应把它压在实测空档上，链路变好即自动降低。
- 若又看到停顿，先看 `--net-stats` 的 `最大连续间隔` 与 `保持`：
  **连续间隔小、保持高**说明原因不在水位（例如成簇投递没被正确处理）；
  **连续间隔本身就大**说明是链路空档，此时水位会自动抬高，仍不够再手工设 `--interp-buffer` 对照。
- 插值逻辑有确定性测试：`tests/remote_interpolator_test.gd`（28 项断言，`tools/net-smoke.mjs` 会先跑它）。
  它断言的核心是“成串到达下每一步位移相同”与“丢弃重复快照后每一步位移相同”，
  用手试不出来，但算得出来。

### 调试开关

- `--net-stats`：每两秒输出一行总览（帧率、帧时范围、物理帧率），
  以及每个角色一行（每秒更新、最大到达间隔、重复比例、停顿比例、缓冲水位、钟速、
  停格帧数、显示移动、收到回拉、显示回拉）。
  **先看 `停顿`**：它就是人看到的"卡一下"，健康值接近 0。
- `--autopilot`：让本机角色沿**各自的出生 Z 坐标**在 X 方向往返，不按键也能量显示平滑。
  **不要写成两人走同一条线**，实测会直接撞在一起；
  也不要用"追一个移动目标点"的写法，角色追到后会停下等目标，产生周期性假停顿，
  把度量本身污染掉。用"到达端点后立即翻转改向"，不要到达后把方向置零——
  置零会让角色留在到达半径内、每帧反复翻转，永远卡在端点。
- 平滑基本不需要调参：水位按实测最大连续间隔自适应（夹 50～350 ms）。
  `--interp-buffer <秒>` 可临时覆盖水位并关闭自适应，仅用于对照
  （例如怀疑 100 ms 空档没被盖住时，试 0.25 看是否缓解）。
- 本机那一行报的是“发送方基准”（`位置更新` 与 `最大间隔`），
  用于和远端行的 `最大到达间隔` 对照，定位空档来源。

## Windows 上跑与结束实例的两个坑（2026-09-24 实测）

- **`Godot_v<版本>-stable_win64_console.exe` 是包装程序**，它会以子进程方式启动
  `Godot_v<版本>-stable_win64.exe`（两者命令行参数相同，只是二进制名不同，开始时间一致）。
  因此 `Stop-Process` 只结束包装进程时，**真正的引擎进程会活下来并继续占着端口**，
  下一次自检就会以"无法监听"的形式失败。要么结束整棵进程树（`taskkill /PID <pid> /T /F`），
  要么直接结束命令行里带真正参数的那个 GUI 进程。
  `tools/net-smoke.mjs` 因此改用 taskkill 结束进程树。
- **`--quit-after` 必须放在 `--` 之前**。放在 `--` 之后它就是一个自定义参数，引擎会静默忽略，
  于是实例永不退出、又看起来"已经跑过了"。我第一次验证断线时就是这样，白等一轮。
- 端口 0 可用：`-- --port 0` 让系统分配空闲端口（实测能监听成功，日志写"监听 UDP 0"，
  所以状态文字在端口为 0 时改成"系统分配的 UDP 端口"）。自检因此不依赖 27015 是否空闲。

## 断线处理

- 主机退出时客户端能察觉：实现在 `_on_server_disconnected` 里先 `Net.close()` 再发信号。
- **注意 `Net.close()` 会把 `multiplayer_peer` 置空，此后 `multiplayer.get_peers()` 会报
  "No multiplayer peer is assigned"**。任何在断线后刷新界面的代码都要先判断会话状态，
  `main.gd` 的 `_describe_peers()` 就是因此加了 `role == OFFLINE` 的前置判断。
  实测：修好前客户端每次断开都会报这个错。
