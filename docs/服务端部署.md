# 服务端部署完整流程

从零开始把《熔霜》的权威服务端放到一台按量计费的云服务器上，供不在同一局域网的两人联机调试。
按顺序做完第三节至第九节即可；第十节是日常操作，第十一节是成本，第十二节是排错，
第十三节记录各项取舍的实测依据，用于判断"能不能换个做法"。

本文以腾讯云 CVM 为例，其他厂商的对应项在括号里注出。

---

## 一、结论速览

| 项目 | 取值 | 说明 |
| --- | --- | --- |
| 实例 | BF1.MEDIUM2（2 核 2G） | 实际负载约为规格的千分之一，选最便宜的档 |
| 计费 | **按量计费** | 断续调试时按小时付费；轻量应用服务器没有这一档 |
| 镜像 | Ubuntu Server 26.04 LTS | 公共镜像，不要应用镜像 |
| 系统盘 | 高性能云硬盘 20 GiB | 最便宜的类型；它是关机期间唯一持续计费的项目 |
| 公网 | **按流量计费** + 5 Mbps 上限 | 按带宽计费在关机期间仍收费 |
| 公网地址 | 弹性公网 IP（EIP） | 不转则每次"关机不收费"之后 IP 会变 |
| 域名 | Cloudflare A 记录，**仅 DNS（灰云朵）** | 橙云只代理 HTTP，不转发 UDP |
| 安全组 | 放行 `TCP:22`、`TCP:27017`、`UDP:40001-40020`、`ICMP` | 购买页那个开关默认关闭，必须在控制台手动加。**两个游戏相关的规则缺一个都是"连不上"**。服务器上**不需要** `UDP:27015`（见 10.5.1） |
| 端口 | `TCP 27017`（房间目录）、`UDP 40001+`（每间房一个） | 房间目录见 `tools/room-directory.py`；**不要用 27016 当房间端口**（那是局域网探测端口） |
| 本机别名 | 在 `~/.ssh/config` 里加 `Host moltenfrost` | **使用前必做**：公网地址不入库，本机就只留这一处；见第五节 |

服务端跑的是**同一份工程源码**，不是导出的产物。服务器上只需要 Godot 的 Linux 二进制与仓库，
不需要导出模板，也不需要编辑器。

## 二、前置准备

1. **实名认证**：未实名无法购买实例。
2. **账户余额**：按量计费开通时会**冻结一小时的主机费用**，且**代金券不能抵扣冻结金额**。
   首次建议充值 20～50 元，足够调很久。
3. **SSH 密钥**：在本机生成一把专用于服务器的密钥，不要复用 GitHub 那把，
   这样私钥泄漏时只需吊销这一台。

```powershell
ssh-keygen -t ed25519 -C "moltenfrost-server" -f $env:USERPROFILE\.ssh\id_ed25519_moltenfrost
# 提示设置密码短语时可以直接回车留空
```

把公钥内容加进腾讯云的密钥对（云服务器 → 密钥对 → 创建 → **使用已有公钥**）：

```powershell
Get-Content $env:USERPROFILE\.ssh\id_ed25519_moltenfrost.pub
```

要选「使用已有公钥」而不是让平台生成，因为生成的私钥只能下载一次，丢了就只能重建实例。

## 三、第一步：创建实例

购买页入口 `https://buy.cloud.tencent.com/cvm`（**不要走「轻量应用服务器」**，
那个只有包年包月，没有按量计费）。

按第一节的表格逐项设：
- **计费模式**：按量计费。默认是包年包月，第一项就要改。
- **地域**：选离使用的人近的。两人分处两地时选中间地域，或各测一次比较 RTT。
- **可用区**：默认即可，不影响使用。
- **实例规格**：BF1.MEDIUM2。蜂驰型的定位是"同规格单价最低"，
  而本工程的负载是每玩家约 120 包/秒、不到 10 KB/s，规格给了 25 万 pps 与 1.5 Gbps。
- **镜像**：公共镜像 → Ubuntu Server 26.04 LTS 64bit。不要选带宝塔/WordPress 的应用镜像。
- **系统盘**：高性能云硬盘，**容量改到 20 GiB**（默认常常给 50）。
  理由见第十一节：它是关机期间唯一照收的项目，压低它对按量计费的意义最大。
- **数据盘**：不添加。
- **公网 IP**：勾选「分配独立公网 IP」。
- **带宽计费模式**：**按流量计费**，上限 5 Mbps。
  这一项最容易忽略：按固定带宽计费时，**关机不收费期间带宽费仍然照收**。
- **登录方式**：密钥，选第二步建好的那一把。
- **其他**：云监控与自动化助手免费，保留；定时销毁不勾。

## 四、第二步：安全组

**购买页那个「安装安全组规则」开关默认关闭，不打开的话目标勾选框全部无效。**
实测的后果是入站规则为空，于是连 TCP 22 都超时，看起来像实例没有启动成功。

因此创建之后到 控制台 → **网络与安全 → 安全组** → 找到实例绑定的那个组 → **入站规则** →
「添加规则」，「+新增一行」一次加齐这四条：

| 类型 | 来源 | 协议端口 | 策略 | 备注 |
| --- | --- | --- | --- | --- |
| 自定义 | `0.0.0.0/0` | `TCP:22` | 允许 | SSH |
| 自定义 | `0.0.0.0/0` | `TCP:27017` | 允许 | 房间目录（HTTP，客户端从这里取房间列表） |
| 自定义 | `0.0.0.0/0` | `UDP:40001-40020` | 允许 | 房间（每间一个端口，客户端**直连**它） |
| 自定义 | `0.0.0.0/0` | `ICMP` | 允许 | 让 `ping` 能用于判断可达性 |

**为什么是 UDP 一段而不是一个端口**：玩家要自己选房间，所以每间房必须有自己的对外
地址与端口（见 `docs/公网房间方案.md` 的路线 A）。放行一段而不是逐个加，是为了以后
多开房间时不必再改安全组；一个房间用掉一个端口，从 40001 起。

**那 20 个端口不是容量上限，只是我随手写的余量。** 代码里没有任何地方限制房间数为 20：
目录自己的上限是 `--max-rooms 64`，而实际能开几间由**内存与 CPU** 决定（见 10.5 的实测）。
写 20 是为了「一次把余量开够，以后加房间不用再进控制台」——范围规则与单端口规则
在控制台里是同一步操作，多放行 19 个端口不花任何代价。
超过 20 间时把那一段改宽（或再加一条规则）即可，**不用改代码**。

**两条游戏相关的规则缺一个都是同一个现象：连不上。** 目录没放行 → 列表拉不到；
房间段没放行 → 列表里有房间但点进去超时。前者界面上会写明"官方房间列表拉不到"，
后者会走到 10 秒连接超时并提示"对方没有回应"。

**这个表里没有 `UDP:27015`，也不需要它。** 27015 是单房间时代的入口，路线 A 之后
官方服务器**不听这个端口**（`sudo ss -lunp` 上只看得到 40001、40002）。
那四条之前开过的旧规则可以直接删掉（见 10.5 末尾"27015 现在还剩什么用"）。

来源填 `0.0.0.0/0` 是因为家庭宽带的公网地址会变，写死具体地址会在某天突然连不上，
而排查时很难联想到安全组。

**ICMP 那一条不影响游戏，加它是为了让 `ping` 有诊断价值。**
不加时 `ping` 一律超时（实测 100% 丢包），而超时本身是模糊的——
分不清是"主机不可达"还是"只是 ICMP 被拦"，于是这个手段就失去了信息量。
加上之后，`ping` 的结果就是可信的：通说明网络层没问题，不通则指向实例状态或安全组。

注意：实例关机时 `ping` 也不通，那是预期行为，不是故障。

保存后立即生效，不需要重启实例。

排查判据：**TCP 超时（而不是拒绝）表示报文被静默丢弃**，也就是安全组没有放行。
注意 `ping` 通不代表 UDP 通，两者在安全组里是分开的条目。

## 五、第三步：连接服务器

```powershell
ssh -i $env:USERPROFILE\.ssh\id_ed25519_moltenfrost ubuntu@<公网IP>
```

首次连接会问 `Are you sure you want to continue connecting?`，答 `yes`。
Ubuntu 镜像的默认用户名是 `ubuntu`，且该用户免密 sudo。

如果登录不了，用控制台的 VNC（实例列表那一行的「登录」）。VNC 走内网通道，
**不受安全组影响**，因此它能进就说明服务器本身正常、问题在安全组。

### 5.1 接着把别名写进 `~/.ssh/config`（建议立刻做）

公网地址**不写进仓库**：它只属于自己的基础设施，且转 EIP 或重建实例后就会变。
本机唯一的落脚点是 `~/.ssh/config`，所以拿到地址后第一个动作就是把它记在那儿：

```text
Host moltenfrost
    HostName <公网IP>
    User ubuntu
    IdentityFile ~/.ssh/id_ed25519_moltenfrost
```

加完验证（不连接，只回显解析结果）：

```powershell
ssh -G moltenfrost | Select-String hostname,user,identityfile
```

好处是**本文下面所有 `<公网IP>` / `<地址>` 都可以写成 `moltenfrost`**，
不必回控制台现查。`tools/deploy-server.mjs` 与 `tools/check-server.mjs` 也接受别名：
两者执行的都是 `ssh -i <私钥> ubuntu@<--host 的值>`，`-i` 与别名可以共存。

## 六、第四步：转弹性公网 IP

**这一步要在第一次关机之前做。**

腾讯云的「关机不收费」会**释放公网 IP**，重新开机拿到新的地址。
不转 EIP 的话，每次开机都要去 Cloudflare 改 A 记录，否则域名指向旧地址，
表现为"连接超时"，很容易误判成服务器没有起来。

计费规则（已核实）：

| 状态 | IP 资源费 |
| --- | --- |
| EIP 已绑定实例（无论实例运行或已关机） | **0**，绑定期间暂停计费 |
| EIP 未绑定（解绑之后、或实例已销毁） | 0.20 元/小时，即 4.8 元/天 |

结论：**只要 EIP 一直绑在这台实例上就没有额外开销**，而转换会保留当前这个 IP，DNS 不用改。

路径：控制台 → 云服务器 → 实例 → 更多 → **IP/网卡** → **转换为弹性公网IP**。

转换之后**确认带宽计费方式仍是「按流量计费」**。若变成按带宽计费，
关机不收费期间带宽费照收，省钱的意义就没了。

**要记住的风险**：以后销毁实例时，记得**手动释放 EIP**。实例销毁后 EIP 变成未绑定状态，
立刻开始 0.20 元/小时计费，而且不会有人提醒你。

**关于弹性网卡（ENI）**：那是另一件东西，用于多网卡隔离与主备切换
（把网卡连同内网 IP、EIP、安全组一起迁到另一台实例上）。
本工程只需要一个公网地址服务一个进程，用它只会增加复杂度，因此不涉及。

## 七、第五步：域名（可选，但推荐）

Cloudflare → 你的域名 → DNS → Add record：

| 字段 | 值 |
| --- | --- |
| Type | A |
| Name | `moltenfrost-server`（或任意子域） |
| IPv4 address | 服务器公网 IP |
| **Proxy status** | **DNS only（灰色云朵）** |

**必须选 DNS only。** 橙色云朵的代理解析返回的是 Cloudflare 的边缘 IP，且它只转发
HTTP/HTTPS 的特定 TCP 端口（80、8080、443、8443 等），**完全不转发 UDP**。
ENet 走 UDP，开着代理必然连不上，而且现象同样是"连接超时"。

也要知道 **Cloudflare Tunnel 解决不了这件事**：它支持 HTTP/HTTPS/TCP/SSH/RDP，
**没有 UDP**；Spectrum 支持任意 TCP/UDP，但属企业版付费功能。

用域名的两个好处：一是不必再记 IP，二是配合 EIP 之后即使换地址也只需改一条记录。

**但目录的 HTTP 不能直接拿域名去发。** 这一点是踩出来的，见 7.1。

### 7.1 目录的 HTTP 要先把域名解析成 IP

**腾讯云会拦截发往未备案域名的 HTTP 请求。** 实测（2026-09-30，同一个 URL 只换主机名）：

| 请求 | 结果 |
| --- | --- |
| `GET http://<域名>:27017/rooms` | **302** → `https://dnspod.qcloud.com/static/webblock.html?d=<域名>:27017` |
| `GET http://106.52.118.93:27017/rooms` | **200**，正常 JSON |
| `POST http://<域名>:27017/rooms/claim` | 200（**这一次**没被拦，但同一台机器上 GET 被拦，不能指望它） |

那个 302 的落点是一页 16780 字节的 HTML（`<!DOCTYPE html>…`），而 Godot 的
`HTTPRequest` **会跟着重定向**，于是客户端拿到 HTML 去 `JSON.parse_string`，
**列表永远拉不到**。客户端日志里是这一句（现在它带上了字节数与开头，就是为这类情形加的）：

```
[dir] 房间目录返回的内容看不懂（16780 字节：<!DOCTYPE html>
<html>

<head>
  <meta http-equiv="X-UA-Compatible" content="IE=edge" />…）（fetch）
```

**因此客户端在启动时把配置里的域名解析成 IP，再用 IP 去连**（`scripts/product_config.gd`
的 `Resolve`）。拦截看的是 HTTP 的 `Host` 头，换成 IP 之后 `Host` 也是 IP，于是绕开了它。

要点：

| | |
| --- | --- |
| 用什么解析 | `IP.resolve_hostname_queue_item(host, IP.TYPE_IPV4)`，**异步**，不在主线程里做 DNS |
| 什么时候 | 入口脚本启动时发起（`begin_resolving`），`_process` 里每帧推进（`pump_resolving`） |
| 解析中怎么办 | 界面**不发请求**（`directory_ready()` 为假），状态栏写「正在解析官方服务器地址…」，否则拿域名去发一次注定被拦的请求，报错会误导成"服务坏了" |
| 失败了怎么办 | 退回用域名（超时 5 秒）。若那个域名已经备案，照样能用 |
| 怎么核对 | 启动日志的 `[config]` 行：`moltenfrost-server.mytemos.com:27017（来自 res://config/product.cfg；域名解析为 106.52.118.93）` |

配置里**存域名**（换机器只改一条 A 记录），IP 是运行期得到的：

```ini
[network]
; 客户端会在启动时把它解析成 IP 再用（腾讯云拦未备案域名的 HTTP，见 7.1）。
official_host="moltenfrost-server.mytemos.com"
official_directory_port=27017
```

而房间的地址仍由服务端的 `--advertise <域名>` 给出（客户端连房间走的是 UDP，
不受这条拦截影响，实测连得上、RTT 20 毫秒）。玩家在列表里看到的仍是域名。

**为什么这条容易白查半天**：它在现象上与"服务端没起来"完全不同——服务活着、
`curl` 也通（`curl` 从**服务器本机**查 127.0.0.1 当然通），只有从公网经域名发
HTTP 才被拦。而"列表拉不到"与"目录挂了"长得一样，于是会去查服务、查安全组、
查防火墙。**判据**：在客户端机器上

```powershell
curl.exe -s -o NUL -w "%{http_code} %{redirect_url}" http://<域名>:27017/rooms
```

看到 `302` 加一个 `dnspod.qcloud.com` 的地址就是它。

**长期解法**（当前没做）：给域名做备案，或者把目录放到一个已备案的域名上。
那时解析这一步自然就不需要了（把 IP 直接写进配置也仍然支持）。

### 7.2 配置文件的形状

界面里「官方服务器」那一栏的房间列表来自 `config/product.cfg` 里的 `official_host`
与 `official_directory_port`，**换机器只改这一个文件**（改完重新启动即生效，不必改代码）：

```ini
[network]
; 目录（HTTP）的地址与端口。**存域名**，客户端启动时解析成 IP 再用（见 7.1）。
; 房间的地址不在这里：它由目录的列表给（每间房自己登记，地址是 --advertise 那个域名）。
official_host="moltenfrost-server.mytemos.com"
official_directory_port=27017
```

改完重启游戏，启动日志里会出现一行
`[config] 官方房间目录：…`，它给出**实际生效**的地址与来源
（文件还是代码里的兜底值）。没看到这行说明改了没生效——这是外部配置最常见的问题。

`config/` 下的普通文本不是 Godot 的"资源"，因此已在两个导出预设里显式列进 `include_filter`。
漏了它的症状是：编辑器里一切正常，而**导出产物读不到配置**（静默回退到代码里的兜底值）。
可用 `node tools/pck-find.mjs <pck> config/product.cfg` 复核产物里到底有没有它。

## 八、第六步：部署

在**本机**（工程目录内）执行：

```powershell
# 首次，或实例销毁重建之后
node tools/deploy-server.mjs --host <公网IP> `
  --advertise moltenfrost-server.mytemos.com --enable-service --directory

# 只更新代码
node tools/deploy-server.mjs --host <公网IP> `
  --advertise moltenfrost-server.mytemos.com --skip-godot
```

两个脚本分工如下，都可单独在对应位置执行：

| 文件 | 在哪里跑 | 做什么 |
| --- | --- | --- |
| `tools/deploy-server.mjs` | 本机 | 准备 Godot 压缩包、打 git bundle、上传、远程调用下一个 |
| `tools/server-setup.sh` | 服务器 | 装运行时库、装 Godot、部署仓库、`--import`、自检、装 systemd |

### 8.1 为什么 `--advertise` 必需

云服务器上 `IP.get_local_addresses()` 只返回 **VPC 私网地址**（本例 `172.16.0.17`），
而公网地址是 NAT 映射的，网卡上根本不存在，程序无从得知。
于是那个"房间在哪里"的地址会指向一个别人连不上的地方。

`--advertise <域名或地址>` 用来覆盖它。**在目录模式下它直接决定房间登记到列表里的地址**
（房间端口由单元里的 `%i` 拼上，每间房不同），生效后日志是：

```text
[session] 启动参数：{ "host": true, "port": 40001, "advertise": "moltenfrost-server.mytemos.com:40001",
                     "directory": "127.0.0.1:27017", "max_players": 2, "lobby": true }
[dir] 已开始向目录 127.0.0.1:27017 登记
[lan] 公网房间不往局域网广播（它在目录里，地址 moltenfrost-server.mytemos.com:40001）
```

**不传 `--advertise` 时房间不会登记一个可用的地址**（会退回网卡上的 VPC 地址），
而目录会老老实实把它存下来——列表里会出现一个指不到的房间。

### 8.2 部署脚本会做的六件事

1. `apt install` Godot 的运行时依赖（是运行时包，不是编译用的 `-dev` 包）
2. 安装 Godot 到 `/opt/godot/godot`
3. **复核动态库**：先 `ldd`，再跑一次 `godot --version` 搜缺失（两步都不能省，见第十二节）
4. 从 bundle 部署仓库到 `~/moltenfrost`
5. `--import` 重建类缓存，并核对 `LanDiscovery` 已注册
6. 起一次服务端做自检；`--enable-service` 时安装 systemd 单元：**目录**
   （`moltenfrost-directory`）与**房间池**（`moltenfrost-pool`）。
   **两者都只在 `--directory` 下装**——单房间模式仍然用 `moltenfrost@<端口>` 那一个模板单元。
   装池的时候会顺手把旧的房间模板单元与它的实例停掉删除（见下面 10.5 的说明）。

### 8.3 工作区必须干净

`deploy-server.mjs` 在**工作区有未提交改动时直接失败**。这不是多余的谨慎：
bundle 只包含已提交的 `main`，未提交的代码不会随它过去，于是服务器上跑旧代码，
**新参数被静默忽略**，表现为"参数传了但没生效"，很难联想到是部署内容的问题。

这条约束来自 `AGENTS.md` 的"两边必须是同一个 commit"。脚本会打印实际部署的 commit，
服务器上也能 `git -C ~/moltenfrost log -1` 复核。

## 九、第七步：验证

### 9.1 服务在跑

目录模式下有**两类进程**：目录 + 房间池。先看它们都活着：

```bash
ssh moltenfrost '
  systemctl is-active moltenfrost-directory moltenfrost-pool
  sudo journalctl -u moltenfrost-directory -n 8
  sudo journalctl -u moltenfrost-pool -n 8
'
```

池的日志里带 `[room <端口>]` 前缀，因此**一个 journal 就能看全部房间**（不需要逐间去 `journalctl -u`）。

再看房间有没有把自己登记上去：

```bash
# 玩家看到的列表（**只有"有人"的房间**）：
ssh moltenfrost 'curl -s http://127.0.0.1:27017/rooms'
# 池里的全部（连备用房一起，用于对账）：
ssh moltenfrost 'curl -s "http://127.0.0.1:27017/rooms?all=1"'
```

**刚部署完时第一条命令返回空列表是对的**，池里只有一间没人进的备用房，而空房不出现在公开
列表里（见 10.5）。第二条应当看到那一间，`busy` 是 `false`。

### 9.2 从本机经公网连上**某一间房**

目录模式下列表里的每一项都是 `host:port`，客户端直连它。但**空房不在列表里**，
所以手工验证要先像玩家一样认领一间：

```bash
# 注意用 **IP**（目录走 HTTP，域名会被腾讯云拦到 DNSPod 的封禁页，见 7.1）
curl -s -X POST http://106.52.118.93:27017/rooms/claim
# → {"ok": true, "host": "moltenfrost-server.mytemos.com", "port": 40001, "name": "房间 40001"}
```

上面那个返回里的 `host` 是**域名**（房间的地址走 UDP，用域名没问题），
而请求用的是 IP。两者不同是故意的，见 7.1。

拿着它给的端口去连：

```powershell
$godot = node tools/setup-dev-env.mjs --print-godot   # 本机 Godot 路径，见 AGENTS.md「环境」
& $godot --headless --path . `
  -- --join moltenfrost-server.mytemos.com --port 40001 --lobby --public-room --net-stats
```

这一条与 `directory-check.sh` 走的是同一条路（它也是先认领再连），所以更省事的做法是直接跑它。

期望 `已连接到主机` → `[lobby] 名单：…`，并且 `[net-stats]` 行有 RTT。

**这一步连不上先查安全组**：`UDP:40001-40020` 没有放行时，目录里能看到房间、
点进去却超时（客户端 10 秒后报"对方没有回应"）。
实测（广州节点）：**RTT 19～21 ms**，帧时稳定 6.9 ms，每秒 60 次位置更新，无丢包。

### 9.3 用界面连

正常运行游戏 → 初始界面。左侧列表里是**别人正在玩的公网房**与局域网里探测到的房间；
选中一间 → 「进入选中的房间」。

**刚部署完（或没人玩）时那份列表是空的，这是对的。**
服务器上总有一间没人进的备用房，但它**不出现在列表里**（否则玩家一打开就看见一堆空壳），
要用只能「认领」。因此想自己开一间公网房：右边把类型选成「公网」再点「创建房间」——
那一下是向目录**认领**那间备用房，它随后就出现在别人的列表里。
进去之后可以在大厅里改房间名（UTF-8，会跟着登记到目录）。

### 9.4 一条命令做完整验收

```powershell
node tools/check-server.mjs --host moltenfrost --advertise <域名>
```

它经真实公网依次检查：SSH 可达 → **服务进程跑的代码与仓库一致** →
**像玩家一样向目录认领一间房**（顺带验证了 `TCP:<目录端口>` 在公网确实通）→
服务在监听 → 经域名连上那一间 → 测得 RTT → **服务端正常停止时客户端不等心跳即发现**。
检查完会把服务恢复成运行状态。

它把两个地址分开用，而且**目录那个是从 `config/product.cfg` 读的**（与客户端同一个来源，
同样的\"先解析成 IP\"那一步）：

| 用途 | 用什么地址 | 为什么 |
| --- | --- | --- |
| 目录的 HTTP（拉列表 / 认领） | `official_host`（域名 → 解析成 IP） | 腾讯云会拦未备案域名的 HTTP，见 7.1 |
| 连房间的 UDP | `--advertise`（域名） | UDP 不受拦截，域名换机器时只改 A 记录 |

最后一条断言是本工具的主要价值：那两个机制在功能上都能"让客户端最终断开"，
只检查"会不会断开"是查不出退化的。因此判据定在**是否短于心跳阈值（5 秒）**。

第二条同样重要：进程跑旧代码时一切看着都正常，只有新改的东西不生效。
这条断言是实打实排掉了一轮误判之后加的（见第十节）。

## 十、日常操作

### 10.1 三种"停止"，用途与花费完全不同

| 操作 | 怎么做 | CPU/内存 | 云盘 | 数据 |
| --- | --- | --- | --- | --- |
| 停目录 | `systemctl stop moltenfrost-directory` | 照收 | 照收 | 保留（列表会拉不到，已连上的对局不受影响） |
| 停房间池 | `systemctl stop moltenfrost-pool` | 照收 | 照收 | 保留（会先逐间请房间自己退出，因此客户端能立刻收到断开通知） |
| 停目录 | `systemctl stop moltenfrost-directory` | 照收 | 照收 | 保留（列表会拉不到，已连上的对局不受影响） |
| 普通关机 | `poweroff`，或控制台关机时选了默认项 | **照收** | 照收 | 保留 |
| **关机不收费** | **控制台**关机，弹窗选「关机不收费」 | 不计费 | 照收（约 13 元/月） | 保留 |
| 销毁实例 | 控制台销毁 | 停止 | 停止 | 回收站保留 2 小时 |

两条容易踩的：

- **在实例内部执行关机（`shutdown`、`poweroff`）不会触发不收费**，
  腾讯云文档明确写了这一条。看起来机器关了，账单照走。
- 控制台关机弹窗**默认是「关机后继续收费」**（API 参数 `StoppedMode` 默认 `KEEP_CHARGING`），
  必须手动改成「关机不收费」。

关机不收费会释放 CPU 与内存，开机时要重新申请资源。资源池紧张时可能启动失败
（报 `NoStock`），过一会儿再试即可，此时实例保持停止状态、只收云盘费。

### 10.2 服务会自己退出与自己启动

- **停止**：`systemctl stop` 发 SIGTERM。**Godot 收到 SIGTERM 是立刻退出，不走 `_exit_tree`。**
  这一点 2026-09-30 重测确认：进程在 **8 毫秒（手工 `kill -TERM`）到 24 毫秒（`systemctl stop`）**
  内就没了，而 `shutdown_gracefully()` 里那六轮 poll（各留 40 毫秒）本身就耍 240 毫秒——
  时间对不上就说明它根本没跑到。
  **因此不能让 SIGTERM 直接落到房间进程上**：单房间模式由单元里的 `ExecStop`
  （哨兵文件 + 最多等 8 秒）把它转成"自行退出"，池模式由池自己逐间请房间退出，
  而后者能成立的前提是 `KillMode=mixed`（见 10.3）。
  单元里设了 `TimeoutStopSec`，把最坏情况的等待从默认的 90 秒压到 15～40 秒。
- **启动**：单元是 `enabled` 状态，开机自启；`network-online.target` 已绑定，
  因此不必担心网络没就绪就绑定端口。开机后约半分钟才在监听，这段时间连不上是正常的。

### 10.3 客户端如何知道服务器下线

两条路径，而它们在 `Net._finish_session` 里**各有自己的文案**——这是判据的根据：

| 场景 | 机制 | 客户端看到什么 | 实测耗时 |
| --- | --- | --- | --- |
| 服务端**自行退出**（`--quit-after`、循环正常结束、`ExecStop`/池的哨兵） | `_exit_tree` → `Net.shutdown_gracefully()`：多轮 `poll()` 让 ENet 的断开通知真正送出去 | 「与主机断开」 | **0.0～1.0 秒**（后者含 ssh 开销） |
| 服务端被**强杀**（崩溃、`kill -9`、断电） | 客户端自己的心跳：连续 `HEARTBEAT_TIMEOUT`（5 秒）收不到 pong 即判下线 | 「与主机失去联系（超过 5 秒没有回应）」 | 5 秒 |
| 服务端被 `systemctl stop` | 期望同第一条 | 期望「与主机断开」 | 见下 |

**第三条曾经落在第二条上（5 秒），2026-10-01 已修。** 原因不在 Godot 那边，而在
单元的 `KillMode`：池模式的池单元当时写着 `KillMode=control-group`（当初是为了
"池停时不留孤儿房间"而显式写下的），而它是把 SIGTERM **同时发给 cgroup 里每一个进程**
——房间也是 cgroup 成员，于是它们 8～24 毫秒就退出了，池那套"逐间请房间自己退出"
的优雅路径根本没机会跑。改成 `KillMode=mixed` 之后：SIGTERM 只给主进程（池有机会先收房间），
主进程退出后 systemd 把剩下的一律 SIGKILL（不会留孤儿），池卡住不退出时
`TimeoutStopSec` 到点同样清干净。实测从 5.0 秒变成 **1.0 秒**，客户端的文案也从
"失去联系"变成"与主机断开"（`tools/check-server.mjs` 第 5 条现在按**文案**判）。

**判据为什么不按耗时。** 那条断言原先判的是"耗时短于心跳阈值"，而计时里含 ssh 握手 +
`systemctl` 的开销，于是同一份代码实测 4.9 秒通过、5.0 秒失败——而那两次其实走的
都是心跳那条路（心跳是在最后一次 ping 之后的 0～5 秒内任意时刻判定的）。
**按文案判既确定又能区分两条路径**，耗时仍然打出来（它确实是"通知 vs 兜底"的量级差别）。

**回归守卫**：`tools/net-smoke.mjs` 里有两条断言配对——
"服务端被强杀后由心跳判定下线"与"服务端自行退出时不等心跳即发现"。
它们验的是前两条路径，**盖不到 `systemctl stop` 那一条**；后者靠 `tools/check-server.mjs`
在真实服务器上跑（它用 `systemctl stop`，因此会如实报出走了哪条路）。

### 10.4 改完代码更新服务器

```powershell
node tools/deploy-server.mjs --host moltenfrost --advertise <域名> --skip-godot
```

Godot 二进制从本机缓存取，一分钟内完成。

脚本会在更新完代码后**自动重启正在运行的单元**，因此不必手动重启，也**不需要**
`--enable-service`（那个开关管的是"安装/启用单元"，与"更新代码"是两件事）。
这一点曾经漏掉，导致服务器上跑着旧代码：那次没带 `--enable-service`，
而"重启在跑的实例"那段当时写在那个分支里面，于是房间池与它端着的备用房
一直在跑部署前那份代码——现象是玩家认领到的那间房报 `rpc node checksum failed`，
而两端各自看都是新版本。

现在重启谁**按"实际上在跑什么"发现**（`systemctl list-units --state=active 'moltenfrost*.service'`），
不看 `--directory`。原因同样是那次教训：本文档给的这条日常更新命令不带 `--directory`，
而旧写法按它拼重启列表，于是它去重启一个早就不存在的单房间单元、
真正在跑的目录与池一个都没动，输出里只有一句 "is not running"，看起来完全正常。

### 10.5 房间是**按需增减**的，不要手工去开

**这里不再有"要开几间"这个决定。** 服务器上跑着一个房间池
（`moltenfrost-pool`，代码在 `tools/room-pool.py`），它每 2 秒问一次目录，
让房间里**恒有 `非空闲数 + --spare` 间**：

```
没人玩        → 1 间空房备着（spare=1），且**不出现在任何人的列表里**
有人开了一间  → 池补上第 2 间备用，别人点「创建」不必等进程启动
人走光        → 多出来的那间被收掉，回到 1 间
```

**空房为什么藏着**：玩家打开界面看到的应当是"现在的房间"，而不是一堆没人进的空壳。
而"创建公网房间"必须立刻拿到一间，所以总得有一间备着——这两条合起来只有一个解：
**备用房存在但不公开，要用就得向目录认领**（`POST /rooms/claim`，见 10.5.2）。

**所以不要再去 `systemctl start moltenfrost@40003` 了**——那个模板单元已经不存在了
（部署时会删掉它）。想多留几间备用就改池的参数：

```bash
# 想让它最多用到 10 号端口、并且多留 2 间备用（改完要 daemon-reload 再 restart）
sudo systemctl edit moltenfrost-pool    # 或者直接改 /etc/systemd/system/moltenfrost-pool.service
sudo systemctl daemon-reload && sudo systemctl restart moltenfrost-pool
```

**那个上限参数决定安全组要放行到哪一号**（`--max-rooms`），因此改大它就要同步改安全组。
上面那条规则放行的是 `40001-40020`，所以到 `--max-rooms 20` 为止都不必再动安全组。

**实际能开几间，看内存与 CPU，不看端口。** 实测（2026-09-30）：

| 项 | 实测值 |
| --- | --- |
| 每间房内存（RSS） | **约 120 MB** |
| 整机可用内存 | 1337 MB / 1930 MB |
| 空载 CPU | 几乎为零（`load average` 0.2） |

因此**内存大约能养 10 间**，而 CPU 是更紧的那一头：2 vCPU，一局对局里服务端要跑
物理与每秒 60 次的位置转发，所以真正的瓶颈在"几局同时在玩"而不是"起了几间房"。

**房间端口号会漂**（池总在端口最小的空号上补房、从端口最大的空闲房收起），
所以安全组要覆盖**整段**而不是某几个号。用 `27016` 当房间端口仍然是不行的：
那是局域网探测端口（见第一节的表），两者共用同一段的话，「27016 连不通」这句话会有两种意思。
同样也不要用 49152 以上：那一段是操作系统的**临时端口**池，与客户端连接的源端口混在一起，
排查时分不清哪个号是房间、哪个号是某个玩家的 NAT 映射。
（该约束与 27015 的取值理由写在 `scripts/net/net.gd` 与 `scripts/net/lan_discovery.gd` 里。）

### 10.5.1 27015 现在还剩什么用

**在这台服务器上：没用了，可以删安全组里那条 `UDP:27015`。**
服务器上不跑任何听 27015 的进程（`moltenfrost@27015` 已 disable，网关也删了）。

**在代码里：还有用，不要删。** 27015 是 `Net.DEFAULT_PORT`，它还管着三件与服务器无关的事：

| 场景 | 为什么还是 27015 |
| --- | --- |
| 本机在界面上创建局域网房间 | 不填端口时的默认值 |
| 「手动连接」里填地址不填端口 | 同上 |
| `--host` / `--join` 不带 `--port` | 与上面两处保持一致 |

也就是说它是**局域网自建房与命令行调试**的默认端口。这类情况下要放行的是
**玩家自己机器的防火墙**（Windows/macOS 首次监听时会弹授权，要允许专用网络），
与云服务器的安全组完全无关。

**为什么当初要特意开它**：单房间时代官方服务器就在 27015 上，那时它是必需的。
换成路线 A 之后入口变成了目录 + 房间段，这条规则就悬空了。

### 10.5.2 「创建公网房间」在服务器上发生了什么

玩家点那一下不是一个本地动作，而是一次 HTTP 请求：

```
客户端 ──POST /rooms/claim──▶ 目录
                              目录把一间**空着的**房间交给它，并保留 15 秒（claim-ttl）
        ◀── {host, port} ─────
客户端 ──UDP 直连那个端口──▶ 那一间房（接下来与局域网建房完全一样：进大厅、等人、房主开局）
```

**为什么必须由目录来交付，而不是客户端自己从列表里挑一间空的**：
列表里根本没有空房（见 10.5），而且**两个人同时点「创建」必须拿到两间不同的房**。
房间要等 2 秒才会把 `players > 0` 报上来，那段窗口只能靠"保留"填，而保留必须是**原子**的。

**"稍等"不是错误**：池要 2 秒对账一次、房间还要一两秒才起来，所以刚把备用房用掉时
目录会回 `{"ok": false, "waiting": true}`，客户端会自己重试（界面上的文案是
「官方服务器正在准备房间，稍等一下…」）。`waiting` 返回的是 HTTP 200，故意不当作错误。

**目录挂了会怎样**：已经在玩的房间不受影响（它们不需要目录），但拉不到列表、
也创建不了新房。这是路线 A 里目录唯一的作用面。

### 10.6 看日志

```bash
journalctl -u moltenfrost-directory -f      # 目录（谁登记了、哪个被认领了、哪个过期了）
journalctl -u moltenfrost-pool -f           # 池（增减房间）+ 每间房的输出（带 [room N] 前缀）
```

房间的输出是**池转发出来的**，因此一个 journal 就能看全部房间，不必逐间 `journalctl`。

## 十一、成本

按量计费 + 公网按流量，广州地域：

| 项目 | 单价 | 备注 |
| --- | --- | --- |
| 实例 BF1.MEDIUM2 | 0.058 元/小时 | 2 核 2G，实测账单显示 `￥0.06/小时` |
| 云盘 高性能 20 GiB | 0.0009 元/GiB/小时 | **关机期间照收**，约 13 元/月，是月度底价 |
| 公网流量 | 0.80 元/GB | 只收出网；两个玩家约 10 KB/s，可忽略 |
| EIP（绑定中） | 0 | 绑定期间暂停计费 |

实际感受：一次 3 小时调试约 **0.17 元**；一直开着一个月约 **42 元**；
关机不收费但保留的一个月约 **13 元**（只有云盘）。

所以调完就关机不收费比较划算，而不必销毁重建——除非停机时间很长
（销毁会把云盘费也停掉，但要重新部署）。这也是把部署脚本写出来的原因：
重建成本足够低时，销毁重来才是可选项。

## 十二、排错

按症状查：

| 症状 | 先查 | 原因 |
| --- | --- | --- |
| SSH 连不上（超时） | 安全组入站规则是否为空 | 购买页那个开关默认关闭，勾选全部无效 |
| VNC 能进但 SSH 不通 | 安全组里有没有 `TCP:22` | 服务器正常，问题纯在安全组 |
| 游戏连不上（SSH 正常） | 安全组里有没有 `TCP:27017` **与** `UDP:40001-40020` | SSH 通不代表游戏端口通，它们是分开的条目。**拉不到列表**＝目录那条没开；**列表有房间但点进去超时**＝房间那段没开 |
| `ping` 不通 | 实例是否在运行 | **关机时 ping 不通是预期行为**；在运行仍不通则看安全组有没有 `ICMP` |
| 域名连不上、IP 能连 | 你看的是哪个端口 | **路由与防火墙都没问题**：域名只用于 UDP（房间），目录的 HTTP 用 IP。见 7.1 |
| 加入界面填的域名连接超时 | 服务端日志里"对方加入时填"那一行 | 云服务器拿不到公网地址，要用 `--advertise` |
| **部署后新改动没生效** | 服务进程是否随部署重启 | 部署只更新文件、不重启进程，进程里仍是旧代码 |
| 部署时提示工作区不干净 | 那不是误报 | bundle 只含已提交内容，未提交的改动不会过去 |
| 服务器上 `git clone` 卡住 | 不要试 | 服务器访问不了 GitHub，必须从本机上传 |
| 启动时报 `cannot open shared object file` | `ldd` 与 `godot --version` 各跑一次 | `ldd` 看不到 dlopen 加载的库 |
| 服务没起来 | `journalctl -u moltenfrost-pool -n 50` 或 `-u moltenfrost-directory` | 看退出码与最后几行。房间拉不起来时池会直接报「拉不起房间 N」与原因 |
| 目录里没有某个房间 | 该房间的日志里有没有 `[dir] 已开始向目录` | 没传 `--directory`，或目录没在跑 |
| 开机后连不上 | 等约半分钟 | 系统启动 + Godot 加载需要时间 |

### 12.0 "部署了但没生效"这一类问题

值得单列，因为它有**三个不同的成因、表象却完全一样**（都是"客户端等 5 秒才断开"），
本轮排查时三个里命中两个：

1. **服务进程跑旧代码。** 部署脚本最初只更新文件、不重启服务，进程里仍是部署前那份代码。
   现在的做法：`server-setup.sh` 发现实例正在运行就 `systemctl restart`，
   而 `check-server.mjs` 会比对**进程启动时间与仓库最新提交时间**，进程更早就直接失败。
2. **改动在实际链路上不成立。** 只 poll 一次在局域网下完全正常，公网下仍不够。
   教训是：局域网里测通过不代表在公网上成立，尤其是与丢包有关的机制。
3. 上面两条都排掉之后，才轮到"代码写错了"。先查前两条更快。

诊断这类问题的可靠办法是**让断言能区分机制**，而不只是看"最终会不会发生"。
例如"客户端最终会不会断开"对三种成因都是"会"，而"是否短于心跳阈值"就能区分。

### 12.1 服务器访问不了 GitHub

实测（2026-09-26，腾讯云广州）：DNS 解析正常（`20.205.243.166`），
但 `curl https://github.com` **超时**；release asset 同样超时；
**六个常见的 GitHub 加速代理与清华镜像全部不通**；只有 `cnb.cool` 通（不托管 Godot）。

因此 Godot 二进制与仓库都**必须从本机上传**。本机侧也不稳定：同一链接实测
先 550 KB/s、再降到 22 KB/s、最后完全超时，`ghfast.top` 代理可用但会劣化到 8.5 KB/s。

**推论：下到手的 Godot 压缩包要留着。** 它缓存在 `build/server/`，
已加进 `.gitignore`（不入库，但也不要清理）。

### 12.2 `ldd` 有盲区

Godot 的 Linux 二进制大部分依赖是直接链接的，另有一小部分在运行期用 `dlopen` 加载。
**`ldd` 只能看到前者。** 实测 `libfontconfig.so.1` 属于后者：`ldd` 报告"全部解析成功"，
而实际启动会打印 `cannot open shared object file`。

它**不会导致启动失败**（只影响字体渲染，无头服务端用不上），因此很容易被当成噪声忽略——
但每次启动都多一行疑似报错，会干扰以后的排查。`server-setup.sh` 因此两步都做，
任一步失败即中止。

顺带一条：**包名随发行版变动**（`libasound2` 在 24.04 起改名 `libasound2t64`），
不要照抄网上的包名列表，要靠上面两步复核。

## 十三、取舍与依据

### 13.1 为什么跑源码而不是导出产物

- 改一行代码只要重新部署一次，不必重新导出与上传几十兆的产物；
- 权威服务端要执行物理与机关判定（设计文档 4.5）。若另用一套实现，
  就要重写刚体动力学、碰撞形状与接触求解，而两套实现必然分叉。
  本项目的核心玩法建立在物理之上，因此服务端与客户端必须是同一份工程。

代价是服务器上要装 Godot 的运行时依赖与二进制（74 MiB 的压缩包），
收益是部署与调试的循环足够短。

### 13.2 为什么选 CVM 而不是轻量应用服务器

**轻量只支持包年包月，没有按量计费。** 断续调试的用法下这一点直接决定选择。
另外轻量不支持绑定 EIP、不能自定义 VPC、公网 IP 在实例生命周期内基本固定，
而这些限制恰好卡在"关机换 IP 时靠域名兜住"这个组合上。

### 13.3 为什么云盘选最便宜的类型与最小容量

负载是"启动时顺序读 60 MB"，之后几乎不碰磁盘（无头服务端只跑物理与网络，
没有资源流式加载、不写数据库）。对比一下：最便宜的「高性能云硬盘」上限 6000 IOPS，
实际需求在个位数。而云盘是**关机期间唯一持续计费**的项目，
所以它决定月度底价，压低它的收益最直接。

### 13.4 为什么官方那边是一个房间目录，而不是一个固定条目

跨网联机时局域网探测本来就收不到对方的广播（受限广播只从默认路由那块网卡发出），
而玩家也不该为了连官方服务器手输一遍域名。因此官方那一侧要有一份**可枚举的房间列表**。

最初的做法是列表最前面放一个固定条目（那一个官方房间）。**换掉它是因为需求变了**：
玩家要自己挑房间，而一个固定条目把"选一间"退化成"只能连那一间"。现在官方服务器上
跑着一个房间目录（`tools/room-directory.py`），每间房自己登记上去，界面拉列表再让玩家选。

**地址不写在代码里，而在 `config/product.cfg`。** 理由是这个值会随部署变化
（换机器、换域名），而它同时被界面、启动脚本与文档引用；写死在代码里的话，
改一次要动好几处，还得重新提交与重新打包。代码里另留一份兜底值，
因此配置文件缺失、键名拼错、类型不对时都能回退，最坏情况只是回到编译时那个地址。

用 `.cfg` 而不是自定义 Resource（`.tres`）的理由：`.cfg` 是普通文本，
任何人拿编辑器都能改，而且**引擎不会改写它**，所以文件里的注释能留住；
`.tres` 由编辑器保存时整份重写，注释必丢（见 `AGENTS.md`）。
代价是 `.cfg` 不被自动识别为资源，要手动写进导出预设的 `include_filter`——
这是一次性配置，比注释随时丢失划算。

测试上不再用"刻意重复写一份常量"那个手法（它建立在常量就在代码里的前提上）。
现在分两层断言：界面用的值等于 `ProductConfig` 解析出来的值（接线），
以及对那个值做**与配置内容无关的属性检查**（非空、含点、不含空格）。
后者能拦住"配置文件被改成了不合法的值"，覆盖面比重复常量更宽。
另外 `tests/product_config_test.gd` 直接校验配置文件的字段结构——
键名拼错时加载器会静默用默认值，而默认值恰好等于文件里的值，
不查结构就完全看不出问题。
