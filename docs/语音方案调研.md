# 熔霜 · 语音方案调研

> 状态：**未调研**。本文件只固定需求、约束与候选路径，等真正要做时再往下填。
> 起因：`机制与玩法设计.md` 的 1.3 与 7.1 —— 不可视状态把实时沟通变成通关条件；打字是必需功能，语音是可选的增强。

## 一、为什么单独开一份

语音与打字是两个独立的决定，不该裹在同一份方案里：

- 打字是**必需功能**：7.1 的不可视状态触发后，被隐藏的一方只能靠语言知道解药在哪。
- 语音是**可选增强**：不做也能玩，但做了会明显降低 7.1 的难度。
- 需要提前记下需求的原因是：语音会影响联机层的通道设计（要不要额外端口、服务端是否转发音频、带宽预算），而联机选型已经定下（设计文档 4.5），以后不想因为语音而推翻它。

## 三、候选路径（都还没验证）

| 路径 | 说明 | 初步顾虑 |
|---|---|---|
| A. 自建转发 | 客户端采集麦克风 → 编码 → 经自建服务端转发给队友，服务端只转发不混音 | 服务端带宽与并发上限直接挂钩（设计文档 4.5 已写明并发上限等于进程数） |
| B. 复用游戏连接 | 语音包与游戏包走同一条 ENet 连接 | 音频包不能挤掉位置同步的包，需要分通道与优先级 |
| C. 第三方 VoIP 服务 | 省掉编解码与转发 | Photon 已在设计文档 4.4 排除；其余服务需单独核许可与价格 |
| D. 不做 | 由玩家自行使用 Discord 等外部工具 | 与 7.1 的关卡难度设定冲突（见第五节） |

## 四、待核实的问题

> 下面这些**都没有实测过**，不要当成结论引用。

- Godot 4 的麦克风采集能否直接拿到可发送的 PCM 帧？实时编码是否必须走 GDExtension？
- Opus 一类编解码在 Godot 4 生态里的现成方案，及其许可是否落在准入清单内。
- 两个平台的麦克风权限：macOS 需要在导出预设的 Info.plist 项里加用途说明（`NSMicrophoneUsageDescription`），否则系统直接不弹授权；Windows 侧行为待测。
- 带宽与延迟：双人语音的实际码率与是否需要语音活动检测（VAD）。
- 与设计文档 4.6 的初始界面 / 房间流程如何衔接：是否开局即开麦、要不要做输入设备选择与音量调节。

## 五、对玩法的影响

- **若最终不做语音**：7.1 的不可视关卡必须保证**打字够用**——解药位置的描述要能用一句短话说清，关卡不要设计成"必须边跑边说"。
- **若做语音**：它必然降低不可视状态的难度，因此关卡的难度要按"有语音"来配，否则带了语音的两人会觉得这一关没有内容。
