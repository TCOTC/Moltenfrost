# 公网房间的技术方案（讨论稿）

> **状态：未定。** 这是给讨论用的候补方案，不是已定决策。
> 拍板之后，结论直接写进本文件正文，未选的路线整节删掉。
> 依据分成两类，全文分开标注：
> **【事实】** —— 已从引擎文档或本项目的实测结论核对过；
> **【待验】** —— 看起来可行但没在本工程里跑过，是本方案里真正的风险点。

## 一、需求

原话：「把官方房间改成支持创建房间，选择公开类型：公网、局域网，匹配到玩家之后才允许点击开始游戏按钮」。

拆成四件事，它们的难度差得很远：

| # | 需求 | 难度 | 说明 |
| --- | --- | --- | --- |
| 1 | 「创建房间」时选公开类型：**局域网** | 没有技术难点 | 就是现在的 `--host`，换一层界面包装 |
| 2 | 「创建房间」时选公开类型：**公网** | **本文的主题** | 现在官方服务器一个实例只承载一局，多房间没有现成做法 |
| 3 | 创建之后先停在**等待房间**，人齐之前不能开局 | 中等，但与公网无关 | 所有路线都要做，做一次就够 |
| 4 | 匹配到玩家（≥2 人）才允许点「开始游戏」 | 同上 | 是大厅界面的一个判断 |

也就是说：需求 3、4 是**公共部分**，先做不会白干；只有需求 2 需要先定路线。

### 1.1 已确认的取舍限制

- **同端口是偏好，不是硬要求**：人倾向于只开一个 UDP 端口。
- **不能接受「结构性代价」**：即「一个房间卡住/崩了，其他房间一起受影响」。
  这一条把「单进程托管所有房间」的做法直接排除。

## 二、现状与硬约束

### 2.1 现在是什么形态

| 项 | 现状 |
| --- | --- |
| 权威节点 | 玩家的**某台机器**（listen server）或云服务器上的一个 headless 进程 |
| 服务器 | 腾讯云 2 核 2G，Godot Linux 二进制 + 同一份工程源码，`systemd` **模板单元** `moltenfrost@<端口>` |
| 端口 | 每局一个 UDP 端口。官方那局对外是 `UDP 27015`（安全组只放行了这一个） |
| 房间发现 | 局域网靠 UDP 广播（`LanDiscovery`，探测端口 27016）；公网靠 `config/product.cfg` 里的域名，写死成一个固定条目 |
| 一局的边界 | **一个进程 = 一个 `MultiplayerAPI` = 一局**。`Game` 的 `@rpc` 全部挂在 `/root/Main/Game`，关卡、玩家、冰块都是这一棵子树里的 |
| 自检 | `tools/net-smoke.mjs` 用 `--host` / `--join` 起两个无头实例，**依赖"连上即开局"** |

`docs/服务端部署.md` 的 10.5 已经写了多开的方式：

```bash
sudo systemctl start moltenfrost@27016      # 第二个房间
```

**但它要求人先知道"要开第二个房间"，并且新端口要同步加进安全组。**
玩家点「创建公网房间」时没有任何人去做这两件事，这就是缺的那一环。

### 2.2 Godot 的机制边界（五条事实）

**【事实 1】一个 `MultiplayerPeer` 绑一个端口，一个 `MultiplayerAPI` 挂一个 peer。**
要在同一个进程里跑多个 ENet server，得给每个房间建一个 `MultiplayerAPI.create_default_interface()`，
再用 `SceneTree.set_multiplayer(api, "/root/Rooms/<id>")` 绑到各自的子树上
（文档另有约束：**不允许嵌套**，且必须在子树 ready 之前设置）。
这条路成立，**但每个房间仍然各占一个端口** —— 它省的是进程，不是端口。

**【事实 2】ENet 的握手里没有应用层字段可直接使用。**
`ENetMultiplayerPeer.create_client(address, port)` 不接受额外数据，握手内容由 ENet 自己生成，
服务端侧的 `ENetMultiplayerPeer` 也读不到。所以「同一个 UDP 端口上按包内容分流」
不能靠现成的 `ENetMultiplayerPeer` 做到，必须换成自定义 peer（见事实 3、4）。

**【事实 3】自定义 `MultiplayerPeer` 可以用 GDScript 实现。**
`MultiplayerPeerExtension` 的类描述写着 "designed to be inherited from a GDExtension plugin"，
但它的两个虚方法明确给出了反例：
`_put_packet_script(buffer)` —— "Called when a packet needs to be sent… **Use this when extending this class via GDScript**"，
`_get_packet_script()` 同理。**结论：单端口分流不需要写 C++。**

**【事实 4】ENet 的握手可以携带 32 位应用数据，且服务端能读到。**

- 客户端：`ENetConnection.connect_to_host(address, port, channels, data)` ——
  "Optional `data` can be passed during connection in the form of a 32 bit integer"
- 服务端：`ENetConnection.service()` 返回 `[EventType, ENetPacketPeer, data, channel]`，
  `EVENT_CONNECT` 的那一项就是客户端送来的值

也就是说**可以用一个 32 位整数把「我要进哪个房间」塞进握手**，服务端在连接建立那一刻就能拿到。
代价是客户端必须用自定义 peer（事实 3）来调 `connect_to_host(..., data)`。

**【事实 5】`MultiplayerSynchronizer` 有按 peer 的可见性，而且它会带走 `MultiplayerSpawner`。**
`set_visibility_for(peer, visible)` / `add_visibility_filter(callable)` / `update_visibility()` / `public_visibility`
都是稳定 API；官方描述里有一句是关键：

> MultiplayerSpawners will handle nodes according to visibility of synchronizers
> as long as the node at `root_path` was spawned by one.

也就是说：把玩家与冰块的**生成与位置同步都限制在自己房间的 peer 集合内**，是引擎提供的正规做法，不是 hack。
这是路线 ① 的全部依托（而 ② 完全用不上它，见下）。

### 2.3 UDP 中转的一个必守实现细节

**不能用一个 socket 替所有客户端转发。** ENet 服务端靠 `(地址, 端口)` 认 peer；
若网关用同一个本地 socket 把所有客户端的包转给房间进程，房间那边会把**所有人看成同一个 peer**，
表现为「两人都连上了，但互相看不见、判定全错」。

所以网关必须做**完整的 NAT**：每个客户端流分配一个自己的本地临时端口（`client_addr → local_socket`），
房间进程看到的就是 N 个不同来源 = N 个 peer。这一条是路线 ② 能不能跑通的判据。

反过来，房间进程**只绑环回**（`ENetMultiplayerPeer.create_server` 的 `bind_ip` 传 `127.0.0.1`），
于是房间端口永远不需要暴露在公网 —— **安全组一条规则都不用改**。

### 2.4 现有代码里会被牵动的前提

| 前提 | 哪条路线会牵动它 |
| --- | --- |
| `Game` 是路径固定的单例（`/root/Main/Game`） | ①（要改成每房间一个实例）；②③④ 不动 |
| `Net`（autoload）假设「本机只有一个会话」 | ①（服务端侧要管多会话）；②③④ 不动 |
| 位置同步 = 各自的机器权威 | ①（跨房间必须靠 visibility 过滤）；②③④ 不动 |
| `Net.host()` 绑通配地址 | ②（房间要改成绑环回）—— 一行的事 |
| 自检依赖「连上即开局」 | 全部路线（引入大厅后要么保留 `--host` 立即开局，要么改自检） |

### 2.5 端口分配

三个号段各管一件事，不要互相借用：

| 号段 | 用途 | 说明 |
| --- | --- | --- |
| `27015` | 公网入口（对外唯一的游戏端口） | 保留，不换。见下 |
| `27016` | 局域网房间探测 | **独占**，且**不要拿来当房间端口** |
| `40000–40099` | 房间实例的游戏端口 | 新增；只绑环回，不对外 |

**`27015` 为什么留**：它的取值只是惯例（Valve Source 系专用服务器的默认端口），
IANA 注册表里 27011–27015 是 Unassigned，这个数字本身没有保证。它「能用」是因为恰好满足三条：

1. **在 1024 以上** —— 否则 Linux 上要 root 或 `CAP_NET_BIND_SERVICE` 才能监听
2. **不在动态/私有段内** —— 那一段（Windows/macOS `49152+`、Linux 默认 `32768–60999`）
   是操作系统的**临时端口**池，绑进去等于跟内核抢号
3. **不撞常见服务** —— 80/443/22/53 都不是它

它已经写进 `config/product.cfg`、安全组规则与部署文档，换它纯亏，**没有理由就不动**。
三条理由已写在 `scripts/net/net.gd` 的 `DEFAULT_PORT` 旁边。

**房间端口为什么必须是 `40000+` 而不是随便取**：② 的网关要给**每个客户端流**分配一个
本地 socket（见 2.3），那些号来自**临时端口范围**。若房间端口也可能落在临时范围内，
排查时就分不出「这个号是某个房间」还是「这个号是某个玩家的 NAT 映射」。
定在 40000 段之后，两类号一眼可分：40000 段是房间，49152+ 是客户端映射。

**为什么只用加一条规则**：房间进程只绑 `127.0.0.1`（见 2.3），
因此 40000 段**不需要**出现在安全组里。对外永远只有 27015。

**`27016` 的坑**：`docs/服务端部署.md` 10.5 原先用 `moltenfrost@27016` 当「第二个房间」的例子，
与同一份文档里的「27016 是探测端口」自相矛盾。已改成 `moltenfrost@40001`。
今天不冲突是因为专用服务端走不到 `listen_for_rooms()`（它不开菜单），
**这是靠启动流程避开的，不是靠代码保证的** —— 而 ② 与 ③ 开始分配房间端口时，
第一个会踩的就是它。

## 三、候补路线

### 路线 ①：单会话 + 应用层房间隔离（同进程，原首选，已排除）

**机制**
一个 ENet server 监听 27015，**所有玩家都连进来**。
服务端在 `/root/Rooms/<room_id>/` 下为每个房间建一棵独立的子树（`LevelHost` + `Players` + `World` + 一个 `Game` 实例）；
玩家按房间分组，靠 `MultiplayerSynchronizer` 的可见性把位置与生成**锁在房间内**。

```
                 ┌──────────── 一个 Godot 进程 ────────────┐
客户端A ─┐       │  ENet server :27015                     │
客户端B ─┼──UDP──▶  ├─ SessionMultiplayer (唯一)           │
客户端C ─┤       │   ├─ /root/Rooms/r1/  ← 可见 r1 的人    │
客户端D ─┘       │   └─ /root/Rooms/r2/  ← 可见 r2 的人    │
                 └─────────────────────────────────────────┘
```

**改动清单**

1. `Game` 从单例改成"每房间一个实例"，所有 `@rpc` 的路径随之带上房间段
2. `main.gd` 增加"房间表"：`room_id → { peers, state, room_name, public }`
3. 玩家与冰块的 `MultiplayerSynchronizer` / `MultiplayerSpawner` 逐个设置可见性
4. `Net` 增加"服务端视角的多会话"接口（`get_peers_of(room)`、`broadcast(room, …)`）
5. 大厅流程（需求 3、4）在服务端侧表现为"房间状态机"

**代价**：四条路线里**唯一要动同步层**的，改动面最大（事实 5 那套可见性要接进现有的插值与心跳体系）。
更关键的是**共享命运**：单个房间的一条 `while true`、一次物理求解炸掉、一次内存爆炸，
**所有对局一起停摆**。这不是"实现得不够好"，而是单进程的固有属性 ——
GDScript 是单线程的，一个房间跑不完，其他房间就没有帧。
（另一个【待验】点是可见性在"生成包"与"可见性变更"上的时序；
但只要共享命运这一条成立，那个时序就不必再验了。）

**结论**：**本路线不再作为候选**，保留在文档里作为对照。

### 路线 ②：单端口 UDP 网关 + 每房间独立进程（① 的改良，推荐）

**思路**：把「单端口」与「进程隔离」拆开拿 —— 这两个要求在 UDP 上是**正交的**。
玩家侧只看到一个 UDP 端口，网关在背后把每个客户端流分流到**各自独立的房间进程**。

```
客户端 ──UDP──▶ :27015 网关（约 200 行，不含任何游戏逻辑）
                 │  NAT 表：client_addr → (room, local_socket)
                 ├──▶ 房间 A：Godot 进程，绑定 127.0.0.1:40001
                 ├──▶ 房间 B：Godot 进程，绑定 127.0.0.1:40002
                 └──▶ 房间 C：Godot 进程，绑定 127.0.0.1:40003
```

**关键性质**

- **客户端零改造。** 它连的是「一个普通 ENet 服务器 :27015」，现有的 `Net.join()`、
  插值、心跳、`shutdown_gracefully` 一行不动。这是本路线最大的优点。
- **房间零改造。** 一局仍然是「一个进程一个 `MultiplayerAPI` 一棵子树」，
  `Game` 不需要变成多实例，`@rpc` 路径不需要带房间段（事实 5 那套可见性也用不上）。
- **进程隔离。** 一个房间崩了只影响那一局，`journalctl -u moltenfrost@40001` 直接定位。
- **端口仍只有一个，且安全组不用改**：房间只绑环回（见 2.3），它们的端口从不对外。
- **网关看不懂游戏流量**（基础版）：它只做数据报转发，不解析 ENet。

**网关必须做对的两件事**见 2.3：每个客户端流一个独立本地 socket；房间只绑环回。

**「进哪个房间」怎么决定**，两种做法，成本差一档：

| | ②a 快速匹配（建议先做） | ②b 从列表选房间 |
| --- | --- | --- |
| 策略 | 新流 → 挑一个未满的房间 | 客户端先取房间列表，选中后再进 |
| 网关要懂 ENet 吗 | **不要**。首次出现的源地址就分配一个房间 | 要。读握手里的房间号（事实 4） |
| 客户端要改吗 | **不要** | 要用自定义 peer 才能送那个 32 位房间号（事实 3） |
| 房间列表从哪来 | 不需要 | 网关或另外的查询接口 |

**建议先做 ②a**：它与第六节 Q2 的「快速匹配空房」是同一件事，
并且把「客户端零改造」这个最大优点保留到最后。

**成本清单**

1. 网关程序（新文件，约 200 行）
2. 网关的 systemd 单元（`Restart=always`）
3. 房间实例的拉起与回收。最省事的是让**网关自己负责**（收到第一条流时启动，最后一人离开后停掉）；
   想避开额外权限就先做「预开 M 个实例 + 网关只挑空的」
4. `Net.host()` 支持绑环回（一行的事）
5. 客户端与同步层：**不动**

**网关用什么写**：它只需要 UDP socket 与一张表，候选见 Q8。

**风险**：网关是新的单点。但它与 ① 的共享命运**不是一个量级**：
它没有物理、没有脚本逻辑、没有关卡资源，只有一个 `sendto` 循环和一张表，
失败模式只有「崩了」与「被 OOM」，配 `Restart=always` 可秒级恢复。
等于把单点从「整个游戏引擎」缩小成「一个几十行的转发器」。

**优点**：同时满足两条硬要求，且客户端与同步层零改造。

### 路线 ③：分配器 + 底层多端口（不想写网关时的替代）

**机制**
对玩家只有一个地址（域名）。客户端先向**分配器**要一个房间，分配器回一个 UDP 端口，客户端再连过去。
**端口对玩家完全不可见**，玩家不需要知道底层开了几局、在哪几个端口上。

```
客户端 ──HTTPS──▶ 域名 (Cloudflare 橙云可以，因为这是纯 HTTP)
                    │  POST /api/rooms  → { host, port }
                    ▼
                  分配器（服务器上）
                    ├─ 探活：哪些端口已经被占
                    └─ 分配：起一个实例 或 挑一个空的
                    ▼
              moltenfrost@27015 / @27016 / @27017 …
```

**为什么分配器可以用 HTTPS**：`docs/服务端部署.md` 里"Cloudflare 必须设灰云"那条约束**只针对游戏流量**——
橙云不转发 UDP。而分配器走的是 HTTP(S)，正是橙云擅长的那部分。所以玩家侧暴露的是一个正常的 HTTPS API。

**分配器跑什么**：服务器上只有 Godot，没有 Node.js。
最低成本是 **Python 3 标准库**（Ubuntu 自带 `python3` + `http.server`），
或者干脆用 Godot 自己写一个 headless 进程（`TCPServer` 手写最小 HTTP）。
**【待验】**：`apt install nodejs` 在本机上能不能装（服务器访问不了 GitHub，但 Ubuntu 源应该是通的）——如果通，用 Node 写会更顺手。

**两个子模型，成本差很多**

| | 预开 + 探活 | 按需启停 |
| --- | --- | --- |
| 做法 | 开机先起 M 个实例，分配器只负责"挑一个空的" | 有人要房才 `systemctl start moltenfrost@<端口>` |
| 服务端权限 | 不需要额外权限 | 要 sudoers 放行 `systemctl start/stop moltenfrost@*` |
| 空转成本 | 没人玩时也占着 M 个进程的内存 | 没人玩时零占用 |
| 回收 | 人走光后实例自己重启回空闲态 | 分配器收尾时 `systemctl stop` |
| 适合 | 先跑通 | 后面再优化 |

**改动清单**

1. 服务端：新增分配器（一个小脚本 + 一个 systemd 单元）
2. 安全组：放行一段 UDP 端口（例如 `27015–27045`，一次加一条范围规则即可）
3. 客户端：`_begin_join_official()` 改成"先请求分配器，再 `Net.join(host, port)`"
4. `config/product.cfg`：官方房间从"一个 host:port"变成"一个 API 地址"
5. 大厅流程：与路线 ① 共用

**成本**：客户端与同步层**几乎零改造**——连上去之后仍然是一局独占一个 ENet server，
现有的插值、心跳、`shutdown_gracefully` 一行不动。新增成本全在服务端那一小段脚本与运维配置上。

**风险**：低。每条机制都是现成的（systemd 模板、ENet 多端口、HTTP API）。
主要不确定是**运维**：分配器自己的可用性（它挂了就没人能建房）、半死房间的回收、
以及"房间列表"要不要做（见第六节）。

**优点**：房间互相隔离，崩一个不影响别人；单房间的资源上限更清楚；出问题时排查面小得多。

**与 ② 的差别**：暴露面不同。③ 对玩家暴露一个 HTTPS API **加一段公开的 UDP 端口范围**；
② 只暴露一个 UDP 端口。③ 不需要写网关，但要写分配器、开端口段，且客户端要多一次「先申请再连」的往返。
**不想写网关程序时，这就是答案。**

### 路线 ④：WebSocket 反代按路径分房间（同端口，但换 TCP）

**机制**
`WebSocketMultiplayerPeer.create_client("ws://域名/room/<id>")`，路径天然区分房间；
Nginx / Caddy 按路径把 WebSocket 转发到后端不同的 Godot 实例。

```
客户端 ──ws://域名/room/r1──▶ Nginx :27015 ──▶ 后端 A（127.0.0.1:40001）
客户端 ──ws://域名/room/r2──▶              ──▶ 后端 B（127.0.0.1:40002）
```

**成本**：同端口、反代是现成设施，看起来最省事。
**代价**：**传输层从 UDP 换成 TCP。** 这条代价在这次改动里是最大的，因为：

- 现有的全部调优都是针对 UDP 的：`RemoteInterpolator` 的水位自适应、`StepAnalyzer`（回拉/重复/空档）、
  `HEARTBEAT_TIMEOUT` 的判定窗口、`shutdown_gracefully` 的多轮 poll——它们都建立在"包会丢、会成簇到达"这个前提上
- TCP 有队头阻塞：一个包丢了，后面所有包一起等重传。而 `memory/networking.md` 里记的实测现象
  （多数间隔 17 ms、偶尔 100 ms 成簇投递）在 TCP 上会变成"要么不抖、要么整段停一下"
- 双人休闲解谜的延迟容忍度比动作游戏高，**所以可能可以接受**，但这是要真机测的，不是能推出来的

**结论**：除非反代设施已经现成、且刻意想要 TCP，否则不选。

---

### 脚注：不再考虑的两种做法

- **单进程 + 按房间分流（事实 3 + 4 确实能做出来）**：用自定义 peer + 握手里的 32 位房间号，
  可以在**一个进程、一个端口**上真正按房间分流。但它解决的是「端口」，不是「共享命运」——
  仍然是单进程，仍然一个房间卡住就全停。所以它正中人明确不接受的那一条，**不选**。
- **`SO_REUSEPORT` + eBPF**：多个进程绑同一个 UDP 端口，由内核按 eBPF 程序分流到不同进程。
  这是 Katran 那一类做法，也是**唯一**能同时做到「同端口 + 多进程 + 精确房间分配」
  而不写用户态网关的方案。代价是要写 C 的 eBPF、要 `SO_ATTACH_REUSEPORT_EBPF`、要 root 与内核支持。
  对一个双人游戏来说杀鸡用牛刀；记在这里只是说明「同端口 + 进程隔离」在极端情况下确实有原生解。

## 四、对比

| | ① 单会话隔离 | **② 单端口网关 + 多进程** | ③ 分配器 + 多端口 | ④ WebSocket 分路径 |
| --- | --- | --- | --- | --- |
| 对外端口 | 1 | **1** | 1 HTTP + 一段 UDP | 1 |
| 服务端进程数 | 1 | M（每房间一个） | M | M |
| **房间故障是否互相影响** | **是（已排除）** | 否 | 否 | 否 |
| 动同步层 | **是，最大** | **否** | 否 | 传输层整体换掉 |
| 动传输层 | 否 | 否 | 否 | **是** |
| **客户端要不要改** | 要（跟着同步层改） | **不要**（②a 完全不用改） | 要（先申请房间） | 要（换 peer 类型） |
| 新增服务端组件 | 无 | 一个约 200 行的网关 | 分配器 | 反代配置 |
| 安全组改动 | 无 | **无**（房间绑环回） | 加一段 UDP | 无 |
| 新增单点 | 整局共享（已排除） | 网关（几十行，无游戏逻辑） | 分配器 | 反代 |
| 2 核 2G 能开几局 | 较多（共享进程开销） | 较少（每房间一份开销） | 同 ② | 同 ② |
| **主要风险** | —（已排除） | 网关的 NAT 实现（见 2.3） | 分配器自身的高可用 | TCP 手感（**【待验】**，且要重测全部同步调优） |

## 五、推荐

**先做 ②a。** 理由：

1. **它是四条里唯一同时满足两条硬要求的**：只开一个 UDP 端口；房间进程互相隔离。
2. **客户端与同步层零改造。** 现有为 UDP 上丢包/成簇投递做的所有调优（`memory/networking.md` 的两条硬结论）
   全部继续成立。这次的收益是「房里多了两个人」，不该拿整条同步链路去换。
3. **它把 ① 的优点保留、把 ① 的代价去掉。** ① 省的是内存与进程数，而 2 核 2G 现在的负载是
   「规格的千分之一」（`docs/服务端部署.md` 13.1），余量大到没必要为省内存承担共享命运。
4. **失败面小**：一局出问题时另外几局不受影响，`journalctl -u moltenfrost@<端口>` 直接定位那一局。
5. **可以分期**：先做「预开 M 个实例 + 网关只挑空的」把链路跑通（不需要额外的 systemd 权限），
   之后再让网关负责按需启停。

**如果不想引入网关程序**，退到 ③：它同样满足两条硬要求，代价是安全组放行一段 UDP 端口
和客户端多一次申请往返。**不要为了「省一个端口」退到 ① 或 ④** ——
前者违反硬要求（共享命运），后者拿传输层去换。

## 七、验证计划

每条路线各有一个"文档说可以、真机不一定"的点。**先花小成本证伪，比写完再发现不行便宜得多。**

### 7.1 路线 ② 的网关原型（**先做这个**，它决定 Q1）

新增 `tools/udp-gateway.mjs`（或 `.py`）＋ 一个手工跑的自检，验证四件事：

1. **两个客户端经网关进同一房间能互相看见** —— 覆盖 2.3 那个 NAT 细节。
   这是最关键的一条：若网关用单 socket 转发，现象就是"两人都连上了但互相看不见"。
2. **两个客户端分别进不同房间，彼此不可见**，且各自的关卡与积分互不影响
3. **杀掉房间 A 的进程**，房间 B 的两个客户端**无感知**（`[net-stats]` 继续流动）——
   这一条直接证明"结构性代价"已消除
4. **网关重启**后新客户端能正常进房（已有连接的恢复策略此时可以只是"重连"）

前两条过了 ② 就成立；第 3 条不过是"进程隔离"的常规结果，但它是人最在意的那条，要亲眼看到。

### 7.2 服务器侧的两件事

1. `apt install nodejs` 在本机上能不能装（决定 Q8）
2. 起 3 个 Godot 房间实例时的实际内存占用，用来定 M 的上限（现在是估的，要实测）

### 7.3 若退到路线 ③

验证 `systemctl start moltenfrost@27016` 由非 root 触发需要什么授权（sudoers 的最小授权范围）。

### 7.4 若考虑路线 ④

把 `Net.host/join` 临时换成 `WebSocketMultiplayerPeer`，在真实公网跑一次 `--net-stats`，
对照现在的 UDP 基线（RTT 19～21 ms、帧时 6.9 ms、每秒 60 次更新、无丢包）。
**重点看 `最大到达间隔` 与 `停顿` 这两项**，它们直接反映队头阻塞。

## 九、菜单视觉方向（已定）

**熔岩 × 冰霜**。理由不只是好看：界面上的"橙 = 熔、蓝 = 霜"必须能直接接到关卡里，
玩家在大厅里学到的色彩语言，进入关卡后要毫无断层。因此强调色不是装饰，是**同一个符号系统的两族**。

具体到实现（全部代码绘制，不引入美术资源，与 `scripts/ui/game_theme.gd` 的既有做法一致）：

| 元素 | 做法 |
| --- | --- |
| 底色 | 暗色石板／玄武岩质感（噪点 + 极缓慢的色温漂移） |
| 标题「熔」「霜」 | 两种材质感：熔侧偏发光、霜侧偏棱角切面 |
| 面板 | 切角（不是圆角）＋ 内侧一道亮边，像金属压边 |
| 主按钮 | 熔岩橙的实心 ＋ 外发光；按下时内凹 |
| 次按钮 | 冰蓝描边 ＋ 深底；悬停时描边亮起 |
| 列表项 | 选中项用冰蓝的左侧色条，而不是整行变色 |
| 大厅玩家条 | 每人一条，左侧一条元素色的竖条（熔/霜），与关卡里的角色胸章同色 |

**需要人确认的**：以上是"熔岩 × 冰霜"的具体落法，字重视角、发光强度这类只能看效果调，
所以实现之后要跑一次 `tests/shot.tscn` 截图给人看，再微调。
