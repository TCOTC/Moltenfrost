# 熔霜 · Moltenfrost 游戏设计文档

> 项目定位：借鉴经典双人元素解谜玩法内核，通过 3D 化重构与 PVE 系统拓展，打造一款**独立原创**的解谜动作游戏。
> 日期：2026-09-23
> 修订：2026-09-23 —— 确定为**仅桌面端**发行，支持 **Windows 与 macOS**（开发用的两台笔记本即这两个系统），各机器只导自己平台的产物；macOS 产物为 Universal 2，但**只支持 Apple Silicon**，Intel Mac 不在支持范围；双人协作为**多台设备联机**，不做单机同屏
> 命名、法律边界与合规调研见 `命名与合规调研.md`

---

## 一、项目概述

### 1.1 玩法内核参考

经典网页双人解谜系列（英文正名 *Fireboy and Watergirl*，中文俗称《森林冰火人》）由独立开发者 Oslo Albet 于 2009 年发布，核心玩法为：

- 双人/单人双控协同闯关
- 两名角色具备相克元素属性（火怕水、水怕岩浆）
- 收集宝石、触发机关、规避属性陷阱
- 纯解谜、无战斗、无成长线

### 1.2 项目目标

在**保留"双元素协同解谜"这一抽象玩法内核**的前提下，完成三件事：

1. **3D 化重构** —— 从 2D 平面卷轴升级为三维空间解谜
2. **PVE 拓展** —— 加入战斗、怪物、成长系统，实现长线运营
3. **彻底原创化** —— 名称、美术、关卡、数值、代码全部自主创作（合规要求见 `命名与合规调研.md`）

## 二、命名

### 2.1 游戏名：熔霜 / Moltenfrost

| 项 | 内容 |
|---|---|
| 中文名 | **熔霜** |
| 英文名 | **Moltenfrost** |
| 意象 | 熔（熔岩·火）+ 霜（寒霜·水），两字均为"临界状态"——熔是固液之间，霜是气固之间 |
| 优势 | 两字极简、读音干脆；不含"冰/火"任何一字，联想风险低；合成词显著性高于 `A & B` 词组结构 |

读音：Moltenfrost 为自造合成词（Molten + frost），重音落在第一音节，英 /ˈməʊltənfrɒst/、美 /ˈmoʊltənfrɔːst/。

### 2.2 角色名：熔 & 霜

| 属性 | 中文 | 英文 | 备选拼音 |
|---|---|---|---|
| 火 | **熔** | Molten | Rong |
| 水 | **霜** | Frost | Shuang |

**设计要点**

- 与游戏名《熔霜》同源，品牌高度统一
- 「熔」「霜」均为状态词而非元素直呼，辨识度高于直呼型命名，且完全原创
- 英文名 Molten / Frost 与游戏名 Moltenfrost 呼应；若担心与游戏名过度重叠，可改用拼音 **Rong & Shuang**，进一步降低商标关联风险
- 造型建议：熔——熔岩结晶体，裂纹中透出橙红流光；霜——冰霜能量体，表面凝霜、边缘折射冷光

## 三、3D + PVE 差异化设计方向

### 3.1 元素反应系统（核心创新）

突破原版"只有两种元素"的设定，构建多元素反应网络：

| 组合 | 效果 |
|---|---|
| 火 + 风 | 火焰蔓延，点燃范围区域 |
| 水 + 雷 | 导电，连锁触发电气机关 |
| 火 + 水 | 蒸汽，产生上升气流或遮蔽视野 |
| 土 + 水 | 泥沼，减速或固化地形 |
| 雷 + 土 | 磁化，吸附金属物件 |

> 这是原版完全不具备的深度，也是玩法原创性的最强证明。

**熔 & 霜 专属反应**

| 组合 | 效果 |
|---|---|
| 熔 + 霜 | 骤冷成器，熔岩凝为可通行平台 |
| 熔 + 霜（水汽） | 蒸汽爆发，推动风车机关或升举重物 |

### 3.2 立体关卡设计

**视角（2026-09-24 定）：第一人称。** 每位玩家各自一套第一人称视角，右手持元素工具。
这么定与 3.5 的「每人独立视角」一致：第一人称下「看见什么」直接等于「站在哪里、朝哪看」，
隐藏路径与信息差都是自然产生的，不需要额外设计机位。代价是看不到自己的身体，
因此角色造型（分块装甲、发光面缝、背包能量核心）主要服务于「让对方看到你在做什么」，
局部细节留给武器与双手。

**美术方向（2026-09-24 定）：科幻设施。** 低饱和冷灰蓝金属为底，大面积暗部；
画面里的亮部几乎全部来自自发光（灯带、能量场、武器枪口与能量件）。
元素色是画面中唯一的饱和色，用来区分归属。颜色与材质的唯一来源是 `scripts/art/palette.gd`。

**已引入的第三方素材（同日）：** 表面贴图取自 ambientCG、环境贴图取自 Poly Haven，全部 CC0，
可商用且无需署名（清单与许可登记见 `THIRD_PARTY.md` 第五节，下载脚本 `tools/fetch-assets.mjs`）。
其中环境贴图（HDRI）不是装饰：金属材质几乎不漫反射，显示的全部是环境反射，
而此前场景的反射来源只有一个纯色环境色，因此所有金属面看起来都像上了漆的塑料——
这是"没有质感"的主要技术原因。**几何仍然是程序化生成的方块组合，尚未引入外部模型**，
因此角色的形体是"方正的分块装甲"而不是真实模型；是否改用外部角色模型待定（需要同时决定骨骼与动画方案）。

- **多层空间**：关卡具备垂直纵深，上下层联动
- **可旋转机关**：3D 空间中的旋转/翻转平台
- **物理交互**：推箱、折射、浮力等基于真实物理引擎的表现
- **视角切换**：部分关卡需切换视角才能发现的隐藏路径

### 3.3 PVE 系统

- **元素克制战斗**：怪物携带元素护盾，仅对应属性角色可破除，强制双人协作
- **长线运营**：副本分普通 / 精英 / 深渊，配合技能树、装备与角色养成，并设多阶段元素机制 BOSS

### 3.4 单人体验优化

- **AI 同伴**：解决原版"必须两个人才能玩"的最大痛点
- **指令系统**：可对 AI 同伴下达"待命 / 跟随 / 触发机关"等指令
- **联机形态**：多台设备，见 3.5

### 3.5 联机形态

- **每个玩家各用一台设备**，双人协作通过联机实现；不做单机同屏双人，因此不需要处理两人共用一套键鼠、共用一台相机的问题
- **每位玩家拥有独立视角**：3.2 的固定机位与视角切换改为每位玩家各自生效，隐藏路径靠各人切换视角发现，而不是两人共享一个画面
- **局域网优先**：同一网络内直连即可验证协作手感；公网联机作为后续拓展

## 四、技术选型

| 项 | 内容 |
|---|---|
| 目标平台 | **仅桌面端**：Windows（x86_64，Intel 与 AMD 通用）与 macOS（Universal 2 产物，支持范围只到 Apple Silicon）；各机器只导自己平台的产物，不做网页版与移动端 |
| 引擎 | **Godot 4**，项目唯一引擎，不引入 Unity 或 Unreal Engine |
| 脚本语言 | GDScript 为主；需要静态类型与 .NET 生态时改用 C#（使用 .NET 版编辑器） |
| 渲染后端 | Forward+（桌面默认），与编辑器预览一致，不需要按平台分流 |
| 物理 | 引擎内置 3D 物理，用于推箱、浮力与折射；Jolt Physics 需在项目设置中显式选中（默认值仍是 GodotPhysics3D） |
| 联机 | 引擎高层多人 API（`MultiplayerAPI`），传输层用 `ENetMultiplayerPeer`（UDP）主机/加入者模式，多台设备互联；不引入 Photon 或 Mirror |
| AI 同伴 | 有限状态机或行为树；引擎没有内置行为树，可用社区插件或自行实现 |

联机、物理与 AI 全部在引擎能力范围内实现，不为上述任何一项引入第三方引擎或中间件。

第三方库仅限于引擎插件层面，准入规则与清单见 4.2 与 4.3。

### 4.1 平台约束

本项目只做桌面端，且要同时覆盖 **Windows 与 macOS**——开发用的两台笔记本就是这两个系统，日常在两边来回切换。**各机器只导自己平台的产物**：Windows 机器只出 Windows 版，Mac 机器只出 macOS 版，跨系统导出带来的坑（可执行位、DMG、签名工具）因此全都不存在。Windows 侧支持 x86_64（Intel 与 AMD 通用）；macOS 侧产物是 Universal 2，但支持范围只到 Apple Silicon，Intel Mac 不在范围内。双人协作为多台设备联机，不做单机同屏（见 3.5）。发行走桌面商店，没有浏览器沙箱与单文件体积上限；输入用桌面原生输入，键鼠与手柄各维护一份完整映射，并支持运行时重绑定。

只做桌面端意味着**不适用**网页端的一整套限制：指针锁定与全屏不需要用户手势触发、音频没有自动播放策略、存档是真实文件系统而不是 IndexedDB、不需要 HTTPS 与 Secure Context。这些限制从选型依据中移除，也不再作为排除任何库的理由。

对第三方库的影响：不再要求"必须是纯 GDScript 插件"，GDExtension 可以正常使用。但仍**优先**选纯 GDScript 插件——它们不携带平台二进制，升级 Godot 时不需要等作者为两个平台重编。

两台机器带来的三类额外工作：

| 项 | 内容 |
|---|---|
| 输入键位 | macOS 的主修饰键是 Cmd（`KEY_META`），Windows 是 Ctrl；同一套快捷键在另一边会别扭，InputMap 需要按平台分支 |
| 高分屏 | macOS 的 Retina 与 Windows 的显示缩放都会改变实际渲染分辨率；描边宽度、准星这类"按像素数"的美术要按设备像素比核对，不能只在一种屏上调好 |
| 工具链 | 自检与构建脚本必须跨平台（优先 Node 单实现，不写 PowerShell 专用逻辑），否则换到另一台笔记本就少掉一半验证能力 |

导出与签名两边并不对称，提前知道可以省一轮返工：

| 项 | Windows（在 Windows 机器上导） | macOS（在 Mac 机器上导） |
|---|---|---|
| 目标架构 | x86_64（Intel 与 AMD 通用，导出默认值） | Universal 2。官方模板里只有 `godot_macos_*.universal` 一个二进制，预设的 `binary_format/architecture` 选 `arm64` 或 `x86_64` 都会因找不到对应文件而导出失败 |
| 签名 | 可选，不签只有 SmartScreen 提示 | **发布给外部用户必须签名并公证**，否则被 Gatekeeper 拦截；需要 Apple Developer 账号。签名与公证只能在 macOS 上做，所以这条链整体留在 Mac |
| 产物流向 | 只产出 Windows 产物 | 只产出 macOS 产物 |

支持范围与产物架构是两件事：产物是 Universal 2，Intel Mac 能运行，但它不在支持范围内（2020 年之前的机型）——**测试与验收必须在 Apple Silicon 机器上做**。若要真正只出 arm64，需要在 Mac 上导出后用 `lipo -thin arm64` 削掉另一半，且必须削在签名之前；是否做这一步留待发布流程确定。

三条附加规则：

1. **代码许可与素材许可分开核查**。插件自带的字体、图标、音效、示例工程美术往往另有许可（例如 GDQuest 的 TPS Demo 代码是 MIT，美术却是 CC-BY-NC-SA）。
2. **登记台账**。每引入一个第三方库，在项目根目录 `THIRD_PARTY.md` 记录名称、版本、许可、来源链接与是否改动过，对应合规调研文档 2.3「资产」中的授权凭证留存要求。
3. **升级 Godot 后回归验证**。插件跟随引擎小版本失效是常态，升级引擎前先跑一遍自检。

### 4.4 备选与排除

改做桌面端之后，"GDExtension 在网页版跑不起来"这一整类排除理由已不成立，下表按新的实际情况重列。

| 项 | 处置 | 原因 |
|---|---|---|
| LimboAI | 备选，暂不引入 | 桌面端可正常使用，行为树功能强于 Beehave；先按 Beehave 起步，复杂度上来再评估替换 |
| Terrain3D、godot-orchestrator、godot-sqlite | 暂不引入 | 技术上可用，但本项目的关卡是手工房间，没有地形、可视化脚本与数据库需求 |
| Debug Draw 3D | 按需引入 | 调试物理射线与碰撞形状时有用，只在开发期开启 |
| Photon | 排除 | 引擎自带 ENet 已满足联机需求，不引入第三方中继或服务器 SDK |
| GDQuest TPS Demo 等示例的美术资源 | 排除 | CC-BY-NC-SA，禁止商用 |
| 任何 GPL / AGPL 插件 | 排除 | 传染性条款与闭源商业发行冲突 |

### 4.5 由选型派生的两条实现约束

**物理引擎必须显式选择。** `physics/3d/physics_engine` 的默认值是 `DEFAULT`，当前等价于 `GodotPhysics3D`，**Jolt 不会自动启用**，必须在项目设置里显式选中。推箱、堆叠与旋转平台这类场景建议用 Jolt；切换后端后手感会变化，参数调优要在选定后端之后再做，不要两套混用。

**联机走 ENet，权威节点自建。** 两个系统都内置 `ENetMultiplayerPeer`（UDP），不需要额外依赖，局域网内直接连 IP 就能验证协作手感（macOS 首次监听端口会弹一次防火墙授权）。

公网形态在 2026-09-24 定为**自建权威服务端**，它与 Steam 数据报中继、EOS P2P 的分歧点只有一个：由谁解决可达性。本项目面向的玩家与两台开发机一样没有公网入口，因此只有“权威节点自带公网地址”这一条能从根上移除这个问题；Steam 侧官方明确写了非 Steam 渠道不保证服务，EOS 侧则是 Godot 绑定由社区维护。自建服务端的代价是一台 VPS 与月度费用，并发能力上限等于进程数。

服务端与客户端是同一个 Godot 工程，以 `--headless` 启动（可参考官方“Exporting for dedicated servers”，它可以在导出预设里选取专用服务端模式并预先剔掉客户端才需要的资源）。这么定不是因为省事，而是因为服务端要执行物理与机关判定：若另用一套实现，就得把 Jolt 的刚体动力学、碰撞形状与接触求解重写一遍，而两套实现必然分叉，这个项目的核心玩法又恰好建立在物理之上。

玩家移动暂时由本机权威判定，推箱与可旋转平台则要在引入时改为服务端权威；是否把玩家移动一并改为“上报输入 + 服务端模拟”要等网络损伤测试的结果，那一步会引入客户端预测与位置回滚（netfox 一类方案）。

2026-09-24 引入元素与协同机关后，判定分工多了一条可循的规则：**看事实在哪一端**。角色位置的事实属于它自己那台机器，因此移动与异元素地形的致死判定都在本机，复位也由本机执行、再经位置同步传播；而“两人是否同时到位”只有在服务端才能看到全局，因此按钮与机关门的判定在服务端，状态用可靠传输广播。这条规则对推箱与旋转平台同样适用：它们的位置事实不可信于任一玩家，所以判定归服务端。

## 五、执行路线建议

1. **第 1 阶段 · 立项合规**：完成官方商标检索与域名注册，确定原创美术方向
